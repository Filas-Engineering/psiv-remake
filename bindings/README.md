# bindings

A flat C interface to the headless game session in `../game` (with `../core` and `../events` behind it), a .NET wrapper over that interface, and a small MonoGame DesktopGL sample that plays the placeholder adventure through it. Nothing here changes the C++ libraries; they are built with their own Makefiles and linked in.

## Build

Needs `clang++`/`clang` and GNU Make 3.81 or later for the native layers, and the .NET 10 SDK for the rest. The Makefile looks for `dotnet` at `~/.dotnet/dotnet`; pass `DOTNET=/path/to/dotnet` to use another. When it is missing, `make` and `make test` do the native layers only, and `make test` says so.

```
make          # ../core, ../events, ../game through their Makefiles, then build/libpsiv_session.*, the C tests, and the .NET projects
make test     # C tests; the C playthrough compared with game_cli; then the C# tests and the sample's headless run
make clean    # build/ and the .NET bin/ and obj/ folders (the sibling libraries keep their builds)
```

`make test` runs, in order:

1. `build/c_tests`: the focused C tests.
2. `game_cli --seed 6 --auto-battle --script ../game/data/scripts/playthrough.txt` and `build/c_playthrough` with the same arguments, each with an empty save directory. The two transcripts must be identical byte for byte, must match `../game/tests/expected/playthrough.txt`, and every file the two runs wrote (autosaves, the manual save, the profile and the clear-data record) must be identical.
3. `dotnet test` on `csharp/Psiv.Session.Tests` (the C# playthrough is compared with both the golden transcript and a fresh `game_cli` run, saves included).
4. ### macOS

As above. The library is `build/libpsiv_session.dylib` with install name `@rpath/libpsiv_session.dylib`; the C tests find it with `-rpath @loader_path`, and the .NET projects copy it next to their assemblies.

### Linux

`make` picks `build/libpsiv_session.so`, links it with `-shared` and the version script `c/exports_linux.map`, and builds the C tests with `-rpath '$ORIGIN'`. The C++ libraries end up inside a shared object; their own Makefiles build them with `-fPIC`, so nothing extra is needed. MonoGame DesktopGL needs SDL2 and OpenAL (shipped in its package for linux-x64 only; on aarch64 install `libsdl2-2.0-0` and `libopenal1`), the X11 libraries SDL2 loads and an OpenGL driver; the sample's font list covers DejaVu, Liberation and Noto. `../tools/linux-check.sh` runs the window under Xvfb with Mesa's llvmpipe software renderer on `scripts/smoke.txt` (see "Platforms" in `../README.md`); its package list is what a bare Ubuntu 24.04 needs.

### Windows

With clang and GNU Make from MSYS2 or similar (`OS=Windows_NT` selects the branch): `build/psiv_session.dll` plus the import library `build/libpsiv_session.dll.a`, exported through `__declspec(dllexport)` (only the `PSIV_API` functions). The tests link the import library and need the DLL next to them, which it is. The sibling Makefiles name their tools without `.exe`, so the build of `game_cli` may need their help on that platform. The .NET projects copy `psiv_session.dll` next to the assemblies. This Makefile branch has not been run; `../tools/windows-check.sh` builds the same DLL, the C tests and the C playthrough with MinGW-w64 directly and runs them under Wine. Paths given to the library (`data_dir`, `core_data_dir`, `save_dir`) are UTF-8 there as everywhere.

To use another build of the library from .NET, set the MSBuild property `PsivNativeDir` to the folder holding it.

### Errors

Every function returns a `psiv_status`, or a plain value where it cannot fail. On anything but `PSIV_OK`, `psiv_last_error(session, &error)` gives the status, a message key, its parameters and the text rendered in the profile's language:

* `PSIV_REFUSED`: the game said no. The key is the game's (`game.refuse.*`) or core's (`equip.*`, `field.*`, battle command keys), exactly what `game::Session` returned.
* `PSIV_INVALID_ARGUMENT`, `PSIV_NOT_FOUND`: the binding's own checks, keys `binding.*` with English text (`binding.null_argument` names the argument, `binding.out_of_range` the argument and the value). `PSIV_NOT_FOUND` also covers reads of state that is not there now: no area, no line, no battle, no shop.
* `PSIV_DATA_ERROR`: `psiv_session_create` could not load the data; the text is the loader's list of problems, and `psiv_data_problems` gives each with its file, line, entry, text key and parameters. Also `psiv_battle_replay` on a record that does not parse or replay (key `binding.bad_record`).
* `PSIV_INTERNAL_ERROR`: an exception inside the library (out of memory and the like). No C++ exception crosses the interface.

`psiv_last_error(NULL, ...)` reports the last failed `psiv_session_create` on the calling thread.

### Ownership

* **Handles**: `psiv_session_create` returns a session the caller frees with `psiv_session_destroy`. The session owns its loaded data. One thread at a time.
* **Returned pointers** (strings, arrays, the contents of structs the library fills): owned by the session, valid until the next call to a function marked `MUTATES` in the header, or until the session is destroyed. Reads never invalidate earlier reads, so a frame calls `psiv_update` once and then reads everything it draws. String fields are never NULL; `""` means none.
* **Arguments**: copied before anything else happens, so a pointer the library returned can be passed back in, even to a `MUTATES` function. The library keeps no pointer of the caller's.
* **Errors**: the record `psiv_last_error` fills has its own storage, valid until the next failing call.
* **Callbacks**: the optional action callback gets a record valid only during the call, and may call `psiv_action_finish` and nothing else.

All strings are UTF-8. Booleans and enums inside structs are `int32_t`, so layouts do not depend on the compiler's enum size; `psiv_sizeof("psiv_battle_event")` and friends let a foreign binding check its mirrors (the C# tests do).

### How the frame loop maps to the session

Each frame:

1. `psiv_update(session, dt_ms, held_direction)`. In the field it runs fixed ticks (`tick_ms`) and walks the leader one cell per `step_ms` of held input; a direction held for less than a tick still counts at the next tick, so a tap turns the leader. In an event it steps the interpreter. Battle and title ignore it.
2. `psiv_mode_get` says what to present:
   * Field: `psiv_field_info_get` (with the area's `music`), `psiv_field_grid`, `psiv_field_enemies`, `psiv_field_points`, `psiv_field_exits`, `psiv_field_actors` (the script actors in the area: where each stands, its facing, whether it is visible; one no script touched stands at the talk point named after it, see `../game/README.md`, "Actors"). `psiv_actor_ids` lists every actor wherever it stands, so a script subject in it but not in `psiv_field_actors` is an actor in another area, and any other subject a character. Act with `psiv_interact`, `psiv_open_menu`, `psiv_party_talk`; `psiv_face` turns in place. For click-to-walk, `psiv_walk_to(x, y)` and then `psiv_walk_step` each frame (or in a loop, running events in between) until it reports anything but `PSIV_WALK_WALKING`.
   * Event: `psiv_line_get` and `psiv_line_confirm`; `psiv_choice_get` and `psiv_choose`; `psiv_can_skip` and `psiv_skip`. With neither a line nor a choice, keep calling `psiv_update`.
   * Battle: `psiv_battle_combatants` and `psiv_battle_options` for the menus, `psiv_battle_set_command` per member (or `psiv_battle_apply_macro`, or `psiv_battle_start_auto` then `psiv_battle_fill_from_auto` each round, or `psiv_battle_fill_auto_round`), then `psiv_battle_resolve_round`, whose typed events the front end plays back. `psiv_battle_play` runs a whole battle at once. The battle can end inside those calls; the mode then says where control went, and `psiv_battle_info_get`, `psiv_battle_combatants`, `psiv_battle_result_get` (rewards paid out, drops, level-ups) and `psiv_battle_record` describe the ended battle, which the game keeps until the next battle starts, `psiv_battle_dismiss`, a new game, a load or the title.
   * Menu (`psiv_menu_kind_get`: field menu, inn, save prompt, name entry) and Shop: the menu and shop functions, then `psiv_close_menu`. From the field menu: party order (`psiv_party_swap`), the macro editor (`psiv_macro_*`), status screens (`psiv_party`, `psiv_member_detail_get`, `psiv_member_abilities`) and the combo log (`psiv_combo_log`, with the recipe count for locked entries).
   * Title: `psiv_new_game`, `psiv_continue_game`, `psiv_load`, `psiv_retry_battle`.
3. `psiv_notices_drain`: arrivals, rewards, autosaves, party talk lines, warnings, each with key, parameters and text; `PSIV_NOTICE_AMBIENT` notices are party talk that came up by itself on arrival, to show without stopping play.
4. `psiv_actions_poll`: presentation actions (moves, fades, cameras, music), from the game's own action queue. With `PSIV_PRESENTATION_INSTANT` (the default) they are already done and only tell the engine what happened (the queue keeps the last 256). With `PSIV_PRESENTATION_WAIT` the event waits on each until the engine calls `psiv_action_finish(handle)` when its animation ends (a script actor's move: `psiv_field_actors` already reports where it ends, so walk the sprite there from where it was drawn and finish the action on arrival); `instant` records are done at once (the rebuild after a skip or a restore), and `PSIV_ACTION_CANCEL` records name actions a skip abandoned.

## The C# wrapper

```csharp
using GameSession s = GameSession.Create(new SessionOptions { DataDirectory = "../game/data", SaveDirectory = "saves", Seed = 7 });
s.NewGame().ThrowIfFailed();
while (running)
{
	s.Update(dtMs, heldDirection);
	switch (s.Mode)
	{
	case Mode.Field: Draw(s.Field()!); break;
	case Mode.Event: if (s.Line() is { } line) ShowLine(line); else if (s.Choice() is { } c) ShowChoice(c); break;
	case Mode.Battle: /* s.Combatants(), s.BattleOptions(i), s.SetCommand(...), s.ResolveRound() */ break;
	}
	foreach (Notice n in s.DrainNotices()) Show(n.Text);
	foreach (PresentationAction a in s.PollActions()) Start(a);
}
```

* `GameSession` owns a `SessionHandle : SafeHandle` and is `IDisposable`. A disposed session throws `ObjectDisposedException`.
* Every value it returns is a managed copy (records such as `FieldView`, `Line`, `Combatant`, `BattleEvent`, `Member`, `ShopInfo`), so the C library's pointer lifetime rule never reaches C# code.
* Game operations return `PsivResult`: `Ok`, or `Error` (a `PsivError` with status, key, parameters and text) when the game refused; `ThrowIfFailed()` turns it into an exception. Bad arguments and internal errors throw `PsivException`; data that does not load throws `PsivDataException`, whose `Problems` list every load problem with its text key. Reads of state that is not there return `null` (`FieldInfo()`, `Line()`, `Shop()`, `BattleInfo()`).
* Enums mirror the C enums; `GameSession.NameOf(kind, value)` gives the library's names.
* `SetActionCallback` is the optional push delivery, through an `UnmanagedCallersOnly` function pointer; the polled `PollActions` is the main path.
* `Field()` returns the whole field view, script actors included (`FieldView.Actors`, records of `FieldActor`); `ActorIds()` lists every actor id wherever the actor stands.
* The game's walk and auto play are `WalkTo`/`WalkStep`, `FillAutoRound` and `PlayBattle`; the ended battle is `BattleInfo()`, `Combatants()`, `BattleResult()` and `DismissBattle()`; records are `BattleRecord()` and `ReplayBattle(record)`; pacing is `PacingTable()`, `PacingAreas()` and `PacingBosses()`. `SessionOptions.CoreDataDirectory` gives core's data directory.
* The field menu's screens: `SwapLineup`, `MacroList` (records of `Macro` and `MacroStep`), `CreateMacro`, `RenameMacro`, `DeleteMacro`, `MoveMacro`, `SetMacroStep`, `RemoveMacroStep`, `MoveMacroStep`, `MemberDetail(member)`, `MemberAbilities(member)` (with skill uses) and `ComboLog()`.
* This round: `EquipPreview(member, piece)` (records `EquipPreview` and `CombatView`), `Description(kind, id)` with `DescriptionKind`, `Inventory(ItemSort)`, `Difficulties()` (records `Difficulties` and `Difficulty`), `MacroFromCombo(recipe, name)`, `Cameras()` (records `Camera`, enum `CameraTarget`), `GameInfo.TitleMusic`, `VictoryMusic` and `DefeatMusic`, `FieldInfo.Music`, `BattleInfo.Music`, `PresentationAction.Duration` and `NoticeKind.Ambient`.
* `Create` refuses a library whose ABI version differs from the wrapper's.

## The sample

```
dotnet run --project monogame/Psiv.Sample -- [--data DIR] [--saves DIR] [--seed N] [--font FILE] [--exit-after-ms N] [--screenshot FILE.png] [--mute] [--window-size WxH] [--fullscreen]
dotnet run --project monogame/Psiv.Sample -- --script FILE --frames N [--saves DIR]      # headless: no window, no sound
dotnet run --project monogame/Psiv.Sample -- --window --script FILE [--screenshot FILE.png] [--mute]   # the window, keys from the script
dotnet run --project monogame/Psiv.Sample -- --dump-audio DIR   # a generated track and three cues as WAV files, and the synthesizer's self-check
```

The data directory is found above the binary or the working directory when `--data` is left out.

Screens read game actions, not keys. Each action has a list of keyboard keys and a list of gamepad buttons; the defaults:

| Action | Keys | Gamepad |
| --- | --- | --- |
| `Up`, `Down`, `Left`, `Right` | arrows | D-pad, left stick |
| `Confirm` (confirm, talk, hurry the battle playback) | Enter, Z, Space | A |
| `Back` (back, leave, stop auto-battle) | Escape, X, Backspace | B |
| `Menu` (field menu) | M, Escape | Start, Y |
| `QuestLog` | Q | left trigger |
| `PartyTalk` (party talk; on the Items page, the next sort order) | T | X |
| `TextLog` | L | right trigger |
| `Skip` (an event's skip) | Tab | Back (shown as Select) |
| `PagePrev`, `PageNext` (field menu tabs, the shop's buy and sell, the status page's stats and abilities) | Left, Right | shoulder buttons, D-pad left and right |
| `Pause` (the pause overlay, in the field and a battle's command menus) | P | Back (shown as Select) |

The mouse walks: a left click on the field walks the leader to that cell (below). F11 toggles borderless fullscreen; it is the window's own key, outside the bindings. Start stays on `Menu`, as before, so `Pause` takes Select, which is otherwise `Skip`: `Skip` is read only while an event runs and `Pause` only in the field and in battle, so the two never compete.

A direction tap turns the leader whichever input it comes from: it goes to the session as held input for that frame. The stick counts past half its travel, along its stronger axis only. Name entry, and naming a macro, take letters and digits from the keyboard (Backspace erases, Enter confirms, Escape cancels a macro name) or from an on-screen character grid: the directions move over it, wrapping at its edges, and the gamepad's `Confirm` button types the letter under the cursor or works the Space, Del and OK cells; the gamepad's `Back` button erases (on an empty macro name it cancels) and its `Menu` button confirms, so a gamepad alone can type. The window reads `GamePad.GetState(PlayerIndex.One)` each frame; with no gamepad, or after it disconnects, its buttons count as up, and a connect or disconnect prints a line. The controller only sees sets of keys and buttons, so headless runs need no device. Hints (the bottom line, the dialogue box, the battle menu, the field menu, the shop) name each action's first binding, from the gamepad when the last key or button that went down was on it.

Bindings live in `controls.json` in the saves directory: an object with one entry per action name, each with `keys` (MonoGame `Keys` names) and `buttons` (MonoGame `Buttons` names, the stick as `LeftThumbstickUp` and so on). The controller loads it when it starts. A missing file gives the defaults; one that does not parse, or names an unknown action, key or button, gives the defaults and logs one line. An action the file leaves out keeps its default, and `Up`, `Down`, `Left`, `Right`, `Confirm` and `Back`, which the menus need, get their default back (with a log line) when the file leaves them unbound. The options screen's Controls page lists every action with its keys and buttons and works through the controller's calls: `Controls()` (every action with its keys and buttons as display strings), `BeginCapture(action)` and `Capturing` (the next key pressed replaces the action's keys, the next button its buttons; Escape cancels; the screens get no input meanwhile), `ClearBinding(action)` (refused for the six actions above, shown as a toast), `ResetControls()` (after a confirm) and `SaveControls()` (on leaving the page).

* Field: the whole window is the map, drawn in 48 px cells (16 px pictures at 3x), so 1280x720 shows about 26 by 15 cells. The camera follows the party leader, stops at the area's edges and centers an area smaller than the window. Tiles depend on the area kind (town: cobbles, slate roofs, plaster walls with windows; field: grass, hedges; dungeon: flagstones, rock, brick). Floors pick one of four variants and an occasional decoration (flowers, pebbles, cracks, moss, a grate) from a hash of the cell's coordinates. A wall with a non-wall cell below shows its front face, others their top, with dark edges toward open cells and a shadow on the floor under them. Exits on the area's edge are pulsing arrows pointing out, others a doorway; chests are closed or open (`active`), shops a stall, rests a bed, and active step hooks a faint rune. A script's `move` or `face` of a party member plays the same way, but the session reports nothing for it: the game keeps only the leader's cell, which scripts do not move, so where a scene puts party members is presentation (see `../game/README.md`, "Actors"). Every picture is generated at startup by `Art` from code: palettes, a few 16x16 character templates (people, creatures) and procedural tiles from a seeded generator. There are no asset files. ### Replacing the drawing

The sample keeps the game out of its drawing code: `SampleController` reads the session after each update and draws through `IDrawSurface` (`Fill` a rectangle, draw `Text`, `Measure` text, `CreateImage` from a pixel array and draw it scaled with `Image`, `Clip` to a rectangle and `Unclip`, which panels use). `MonoGameSurface` implements it with a `SpriteBatch`, one texture per image and FontStashSharp; `RecordingSurface` is the headless one, which checks image handles and sizes, counts draws and needs no graphics device. Animation runs on a clock that advances only by the frame times the controller gets, so headless runs stay deterministic. To put real art behind the same screens, change what `Art` hands the surface (load sprite sheets instead of generating pixels), implement `IDrawSurface` over another renderer, or replace a screen's `Draw*` method and keep its `Update*` method, which holds all the session calls; each screen's pair is in its own `SampleController.<Screen>.cs` file. For a real game, keep the frame loop of the section above and write the screens from scratch: everything they need comes from the records `GameSession` returns, and animations hook in through `Presentation.Wait` and `FinishAction`.

### Audio

Everything the sample plays goes through `IAudioOut` (`Audio.cs`): `PlayMusic(track, fadeMs)` (one track at a time; the next fades in while the last fades out), `StopMusic(fadeMs)`, `PlayAmbient(sound, fadeMs)` and `StopAmbient(fadeMs)` (one loop), `PlayCue(cue)` (one-shot), `SetVolumes(music, ambient, effects)` and `Update(dtMs)`, with `Music` and `Ambient` saying what plays. `RecordingAudio` is silent and logs every call, which headless runs assert on (`expect audio`); `MonoGameAudio` keeps the same state and log and plays through `SoundEffect` instances, looped for music and ambient, with each group's volume times its fade.

There are no sound files. `Synth` generates 16-bit mono PCM at 22050 Hz in code, as `Art` does pictures: sine, square, pulse, triangle, saw and filtered noise, note envelopes, glides and a step sequencer. A track is an eight-bar loop of sixteen steps: a lead walking a scale and landing on chord tones, a bass on the chord roots, an arpeggio and noise drums, its tempo, scale, root, chords, patterns and lead waveform drawn from a hash of the id, its mood from the id's prefix (`battle`, `dungeon_`, `town_`, `title`). An ambient loop (four seconds, end blended into start) is wind, surf, drips or a hum by the hash. Any cue id gets two to four hashed tones; the sample's own cues are shaped in one table. So every id a script names sounds different with nothing authored per id, and the table overrides the ones the sample uses. Cues are generated when the window starts, tracks and loops the first time each plays; every buffer is normalized to 70% of full scale.

What plays:

* Music, from the data first (`psiv_game_info`'s title, victory and defeat tracks, `psiv_battle_info`'s encounter track, `psiv_field_info`'s area track): the title's track at the title; a script's track from `music play` until the event ends (`music stop` and `music fade` silence it until then); otherwise during a battle the encounter's track, the victory track on a won battle's result screen and the defeat track on a game over's; otherwise the area's track, which comes back after a battle and when an event ends. Where the data names none the ids are derived as before: `title`, `battle_<kind>` (`battle_town`, `battle_field`, `battle_dungeon`) for visible and random battles and `battle_scripted` for an event's battle, nothing on a result screen, and `<kind>_<area>` (`town_tidewater`). Changes crossfade over 800 ms. The placeholder names a track for every area, the title, victory, defeat and the marsh and warden encounters; the training encounter's battles still use the derived ids.
* Ambient: a script's `ambient play` loop until `ambient stop` or the end of the event; none otherwise.
* Script audio actions: `music play` and the ambient actions are done at once, `music fade` when its seconds are up, `sound` plays its cue and is done at once. `instant` ones (the rebuild after a skip or a load) switch without a fade, so loading the autosave before a scene's battle brings back the scene's music and wind; a skip issues no sounds (the interpreter drops them) and leaves music and ambient where the scene left them.
* Cues (`Synth`'s table): `cursor` (a direction on a menu, the title, a choice or a battle menu), `confirm`, `back`, `refuse` (a refusal the session reports; it replaces the confirm), `menu_open` and `menu_close` (into and out of any menu, shop, inn, log, options, pause or load screen), `text` (while a line reveals, at most one per 70 ms), `line` (a line moved on), `save` (a manual save), `step` (the leader's step in the field, at most one per 200 ms), `battle_start`, and from the battle's events as their lines play back, mapped in `SampleController.BattleCue`: `hit` (damage), `miss`, `critical`, `heal` (healed or revived), `status` (a status or stat change landing), `enemy_down` (an enemy falls), `victory`, `game_over`, and `level_up` from the level-up notice.
* Volumes: the profile's music, ambient and effects volumes, read every frame, so a change in Options applies at once.

Devices: headless runs always use `RecordingAudio`. The window uses `MonoGameAudio` unless `--mute` is given; when MonoGame cannot open an audio device (CI, Xvfb, containers, `ALSOFT_DRIVERS` naming no backend) the window logs one `audio: no device (...)` line and runs with `RecordingAudio`, and a device lost later logs one line and goes silent. `--dump-audio DIR` writes `music_town_tidewater.wav`, `cue_confirm.wav`, `cue_hit.wav` and `cue_level_up.wav` and runs the self-check.

## Changes a host must make

This round: `PSIV_ABI_VERSION` 7, library version 0.6.0. Four struct layouts and one enum changed; everything else is an addition.

* Struct layouts: `psiv_game_info` adds `title_music`, `victory_music` and `defeat_music` at the end; `psiv_field_info` adds `music`; `psiv_battle_info` adds `music`; `psiv_action` adds `duration` (a double: how long the action lasts by the data's durations, else its own `seconds`).
