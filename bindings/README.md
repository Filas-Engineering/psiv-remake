# bindings

A flat C interface to the headless game session in `../game` (with `../core` and `../events` behind it), a .NET wrapper over that interface, and a small MonoGame DesktopGL sample that plays the placeholder adventure through it. Nothing here changes the C++ libraries; they are built with their own Makefiles and linked in.

## Build

Needs `clang++`/`clang` and GNU Make 3.81 or later for the native layers, and the .NET 10 SDK for the rest. The Makefile looks for `dotnet` at `~/.dotnet/dotnet`; pass `DOTNET=/path/to/dotnet` to use another. When it is missing, `make` and `make test` do the native layers only, and `make test` says so.

```
make          # ../core, ../events, ../game through their Makefiles, then build/libpsiv_session.*, the C tests, and the .NET projects
make test     # C tests; the C playthrough compared with game_cli; then the C# tests and the sample's headless run
make clean    # build/ and the .NET bin/ and obj/ folders (the sibling libraries keep their builds)
make package  # self-contained builds of the sample per platform under ../dist (below, "Packaging")
```

As above. The library is `build/libpsiv_session.dylib` with install name `@rpath/libpsiv_session.dylib`; the C tests find it with `-rpath @loader_path`, and the .NET projects copy it next to their assemblies.

### Linux

`make` picks `build/libpsiv_session.so`, links it with `-shared` and the version script `c/exports_linux.map`, and builds the C tests with `-rpath '$ORIGIN'`. The C++ libraries end up inside a shared object; their own Makefiles build them with `-fPIC`, so nothing extra is needed. MonoGame DesktopGL needs SDL2 and OpenAL (shipped in its package for linux-x64 only; on aarch64 install `libsdl2-2.0-0` and `libopenal1`), the X11 libraries SDL2 loads and an OpenGL driver; the sample's font list covers DejaVu, Liberation and Noto. `../tools/linux-check.sh` runs the window under Xvfb with Mesa's llvmpipe software renderer on `scripts/smoke.txt` (see "Platforms" in `../README.md`); its package list is what a bare Ubuntu 24.04 needs.

### Windows

With clang and GNU Make from MSYS2 or similar (`OS=Windows_NT` selects the branch): `build/psiv_session.dll` plus the import library `build/libpsiv_session.dll.a`, exported through `__declspec(dllexport)` (only the `PSIV_API` functions). The tests link the import library and need the DLL next to them, which it is. The sibling Makefiles name their tools without `.exe`, so the build of `game_cli` may need their help on that platform. The .NET projects copy `psiv_session.dll` next to the assemblies. This Makefile branch has not been run; `../tools/windows-check.sh` builds the same DLL, the C tests and the C playthrough with MinGW-w64 directly and runs them under Wine. Paths given to the library (`data_dir`, `core_data_dir`, `save_dir`) are UTF-8 there as everywhere.

To use another build of the library from .NET, set the MSBuild property `PsivNativeDir` to the folder holding it.

## Packaging

`make package` (here or at the repo root) runs `../tools/package.sh`, which builds a self-contained, runnable copy of the sample per platform under `../dist/` (git-ignored): `dist/psiv-sample-VERSION-RID/` for `osx-arm64`, `osx-x64`, `linux-x64`, `linux-arm64` and `win-x64` (`../tools/package.sh RID ...` builds some of them). VERSION is the library version, `PSIV_BINDING_VERSION` in `c/psiv_session.cpp`, which `psiv_version()` reports, the sample's `--version` prints and its title screen shows in the top right corner. Each package holds:

* the sample from `dotnet publish -c Release -r RID --self-contained` (no .NET install needed), with the `psiv_session` library built for that platform beside it (through `PsivNativeDir`) and MonoGame's SDL2 and OpenAL where its package ships them (not for linux-arm64);
* `game/data` and `core/data`, in that relation because `game.json` reaches core's data as `../../core/data`, and `game/assets` when the repo has one; the sample finds them beside the program;
* `README.txt`: how to run it, where saves and `controls.json` live (`saves/` beside the program), the common flags and what the platform needs (SDL2 and OpenAL from the system on linux-arm64).

For macOS also `dist/psiv-sample-VERSION-RID.app`: the published sample and a launcher script in `Contents/MacOS` (`psiv-sample`, which passes `--saves "$HOME/Library/Application Support/Psiv Sample"`; a `--saves` given to it wins), the data and README in `Contents/Resources`, where the sample looks for its data before anywhere else. Nothing is signed or notarized; the arm64 binaries carry the ad hoc signatures the .NET SDK's apphost step and the linker always add.

The native libraries come from `../tools/build-native.sh`, which compiles core, events, game and the C API from source with `-O2` into one shared library with its export list, without the Makefiles: macOS with the host's `clang++` and `-arch` (both architectures on Apple silicon), Linux with g++ in the Docker images `../tools/linux-check.sh` builds (`psiv-linux-check` for the host's architecture, `psiv-linux-checklinux-amd64` for `PSIV_LINUX_PLATFORM=linux/amd64`; the C++ runtime linked in statically), Windows with MinGW-w64 in the image `../tools/windows-check.sh` builds (`-static`). The repo is mounted read-only and copied inside; only the library comes back. A target whose library cannot be built here (no Docker, no image, no toolchain for the architecture) is skipped with the reason and not packaged. Everything is built under `dist/.build` (objects, libraries, `dotnet publish --artifacts-path`), never in `build/` or the projects' `bin/` and `obj/`.

Checks, any of which fails `make package`: each package's layout (program, library, data with `core_data` resolving, README.txt) and the architecture of its program and library; on macOS the headless smoke run (`scripts/smoke.txt`, 2000 frames, fresh saves) from copies of the package and of the .app (through its launcher) outside the repo, the x86-64 ones under Rosetta; on Linux, in the same images, the headless smoke run and then the window on `scripts/smoke.txt` under Xvfb, its screenshot checked by `../tools/check_png.py` and kept as `dist/.build/shots/package_RID.png` (`PSIV_PACKAGE_WINDOW=0` skips the window); for Windows the DLL's exports (exactly the header's `PSIV_API` functions, as `windows-check.sh` checks) and the layout only, since nothing runs it. The Linux window runs without `linux-check.sh`'s `ALSOFT_DRIVERS=null`, which crashes the OpenAL MonoGame ships for x86-64; with no sound device the sample logs that and plays silently. Each package is about 90 MB.

### Errors

Every function returns a `psiv_status`, or a plain value where it cannot fail. On anything but `PSIV_OK`, `psiv_last_error(session, &error)` gives the status, a message key, its parameters and the text rendered in the profile's language:

* `PSIV_REFUSED`: the game said no. The key is the game's (`game.refuse.*`) or core's (`equip.*`, `field.*`, battle command keys), exactly what `game::Session` returned.
* `PSIV_INVALID_ARGUMENT`, `PSIV_NOT_FOUND`: the binding's own checks, keys `binding.*` with English text (`binding.null_argument` names the argument, `binding.out_of_range` the argument and the value). `PSIV_NOT_FOUND` also covers reads of state that is not there now: no area, no line, no battle, no shop.
* `PSIV_DATA_ERROR`: `psiv_session_create` could not load the data; the text is the loader's list of problems, and `psiv_data_problems` gives each with its file, line, entry, text key and parameters. Also `psiv_battle_replay` on a record that does not parse or replay (key `binding.bad_record`).
* `PSIV_INTERNAL_ERROR`: an exception inside the library (out of memory and the like). No C++ exception crosses the interface.

`psiv_last_error(NULL, ...)` reports the last failed `psiv_session_create` on the calling thread.

### Ownership

* **Handles**: `psiv_session_create` returns a session the caller frees with `psiv_session_destroy`. The session owns its loaded data. One thread at a time.
* **Returned pointers** (strings, arrays, the contents of structs the library fills): owned by the session, valid until the next call to a function marked `MUTATES` in the header, or until the session is destroyed. Reads never invalidate earlier reads, so a frame calls `psiv_update` once and then reads everything it draws. String fields are never NULL; `""` means none.
* **Arguments**: copied before anything else happens, so a pointer the library returned can be passed back in, even to a `MUTATES` function. The library keeps no pointer of the caller's.
* **Errors**: the record `psiv_last_error` fills has its own storage, valid until the next failing call.
* **Callbacks**: the optional action callback gets a record valid only during the call, and may call `psiv_action_finish` and nothing else.

All strings are UTF-8. Booleans and enums inside structs are `int32_t`, so layouts do not depend on the compiler's enum size; `psiv_sizeof("psiv_battle_event")` and friends let a foreign binding check its mirrors (the C# tests do).

### How the frame loop maps to the session

Each frame:

1. `psiv_update(session, dt_ms, held_direction)`. In the field it runs fixed ticks (`tick_ms`) and walks the leader one cell per `step_ms` of held input; a direction held for less than a tick still counts at the next tick, so a tap turns the leader. In an event it steps the interpreter. Battle and title ignore it.
2. `psiv_mode_get` says what to present:
   * Field: `psiv_field_info_get` (with the area's `music`, its `region`, the vehicle the party rides in `aboard` and the leader's time per cell in `leader_step_ms`, which a renderer glides the leader over), `psiv_field_vehicles` (the party's vehicles in the area), `psiv_field_grid`, `psiv_field_enemies`, `psiv_field_points`, `psiv_field_exits`, `psiv_field_actors` (the script actors in the area: where each stands, its facing, whether it is visible; one no script touched stands at the talk point named after it, see `../game/README.md`, "Actors"). `psiv_actor_ids` lists every actor wherever it stands, so a script subject in it but not in `psiv_field_actors` is an actor in another area, and any other subject a character. Act with `psiv_interact` (which also boards a vehicle ahead and opens an open port), `psiv_leave_vehicle` aboard, `psiv_open_menu`, `psiv_party_talk`; `psiv_face` turns in place. For click-to-walk, `psiv_walk_to(x, y)` and then `psiv_walk_step` each frame (or in a loop, running events in between) until it reports anything but `PSIV_WALK_WALKING`.
   * Event: `psiv_line_get` and `psiv_line_confirm`; `psiv_choice_get` and `psiv_choose`; `psiv_can_skip` and `psiv_skip`. With neither a line nor a choice, keep calling `psiv_update`.
   * Battle: `psiv_battle_combatants` and `psiv_battle_options` for the menus, `psiv_battle_set_command` per member (or `psiv_battle_apply_macro`, or `psiv_battle_start_auto` then `psiv_battle_fill_from_auto` each round, or `psiv_battle_fill_auto_round`), then `psiv_battle_resolve_round`, whose typed events the front end plays back. `psiv_battle_play` runs a whole battle at once. The battle can end inside those calls; the mode then says where control went, and `psiv_battle_info_get`, `psiv_battle_combatants`, `psiv_battle_result_get` (rewards paid out, drops, level-ups) and `psiv_battle_record` describe the ended battle, which the game keeps until the next battle starts, `psiv_battle_dismiss`, a new game, a load or the title.
   * Menu (`psiv_menu_kind_get`: field menu, inn, save prompt, name entry, port) and Shop: at a port, `psiv_travel_destinations(PSIV_TRAVEL_PORT)` and `psiv_travel`; from the field menu, an item or technique whose `travel` kind is set goes through `psiv_travel_destinations` and `psiv_travel` too (`psiv_use_item` and `psiv_use_ability` refuse it). the menu and shop functions, then `psiv_close_menu`. From the field menu: party order (`psiv_party_swap`), the macro editor (`psiv_macro_*`), status screens (`psiv_party`, `psiv_member_detail_get`, `psiv_member_abilities`) and the combo log (`psiv_combo_log`, with the recipe count for locked entries).
   * Title: `psiv_new_game`, `psiv_continue_game`, `psiv_load`, `psiv_retry_battle`.
3. `psiv_notices_drain`: arrivals, rewards, autosaves, party talk lines, warnings, each with key, parameters and text; `PSIV_NOTICE_AMBIENT` notices are party talk that came up by itself on arrival, to show without stopping play.
4. `psiv_actions_poll`: presentation actions (moves, fades, cameras, music), from the game's own action queue. With `PSIV_PRESENTATION_INSTANT` (the default) they are already done and only tell the engine what happened (the queue keeps the last 256). With `PSIV_PRESENTATION_WAIT` the event waits on each until the engine calls `psiv_action_finish(handle)` when its animation ends (a script actor's move: `psiv_field_actors` already reports where it ends, so walk the sprite there from where it was drawn and finish the action on arrival); `instant` records are done at once (the rebuild after a skip or a restore), and `PSIV_ACTION_CANCEL` records name actions a skip abandoned.

## The C# wrapper

```csharp
using GameSession s = GameSession.Create(new SessionOptions { DataDirectory = "../game/data", SaveDirectory = "saves", Seed = 7 });
s.NewGame().ThrowIfFailed();
while (running)
{
	s.Update(dtMs, heldDirection);
	switch (s.Mode)
	{
	case Mode.Field: Draw(s.Field()!); break;
	case Mode.Event: if (s.Line() is { } line) ShowLine(line); else if (s.Choice() is { } c) ShowChoice(c); break;
	case Mode.Battle: /* s.Combatants(), s.BattleOptions(i), s.SetCommand(...), s.ResolveRound() */ break;
	}
	foreach (Notice n in s.DrainNotices()) Show(n.Text);
	foreach (PresentationAction a in s.PollActions()) Start(a);
}
```

* `GameSession` owns a `SessionHandle : SafeHandle` and is `IDisposable`. A disposed session throws `ObjectDisposedException`.
* Every value it returns is a managed copy (records such as `FieldView`, `Line`, `Combatant`, `BattleEvent`, `Member`, `ShopInfo`), so the C library's pointer lifetime rule never reaches C# code.
* Game operations return `PsivResult`: `Ok`, or `Error` (a `PsivError` with status, key, parameters and text) when the game refused; `ThrowIfFailed()` turns it into an exception. Bad arguments and internal errors throw `PsivException`; data that does not load throws `PsivDataException`, whose `Problems` list every load problem with its text key. Reads of state that is not there return `null` (`FieldInfo()`, `Line()`, `Shop()`, `BattleInfo()`).
* Enums mirror the C enums; `GameSession.NameOf(kind, value)` gives the library's names.
* `SetActionCallback` is the optional push delivery, through an `UnmanagedCallersOnly` function pointer; the polled `PollActions` is the main path.
* `Field()` returns the whole field view, script actors included (`FieldView.Actors`, records of `FieldActor`); `ActorIds()` lists every actor id wherever the actor stands.
* The game's walk and auto play are `WalkTo`/`WalkStep`, `FillAutoRound` and `PlayBattle`; the ended battle is `BattleInfo()`, `Combatants()`, `BattleResult()` and `DismissBattle()`; records are `BattleRecord()` and `ReplayBattle(record)`; pacing is `PacingTable()`, `PacingAreas()` and `PacingBosses()`. `SessionOptions.CoreDataDirectory` gives core's data directory.
* The field menu's screens: `SwapLineup`, `MacroList` (records of `Macro` and `MacroStep`), `CreateMacro`, `RenameMacro`, `DeleteMacro`, `MoveMacro`, `SetMacroStep`, `RemoveMacroStep`, `MoveMacroStep`, `MemberDetail(member)`, `MemberAbilities(member)` (with skill uses) and `ComboLog()`.
* This round: `EquipPreview(member, piece)` (records `EquipPreview` and `CombatView`), `Description(kind, id)` with `DescriptionKind`, `Inventory(ItemSort)`, `Difficulties()` (records `Difficulties` and `Difficulty`), `MacroFromCombo(recipe, name)`, `Cameras()` (records `Camera`, enum `CameraTarget`), `GameInfo.TitleMusic`, `VictoryMusic` and `DefeatMusic`, `FieldInfo.Music`, `BattleInfo.Music`, `PresentationAction.Duration` and `NoticeKind.Ambient`.
* Vehicles and travel: `Board`, `LeaveVehicle`, `FieldVehicles()` (records `FieldVehicle`, also `FieldView.Vehicles`), `TravelDestinations(TravelKind)` (records `TravelDestination`), `Travel(kind, destination, user, thing)`; `FieldInfo.Region`, `Aboard` and `LeaderStepMs`, `BattleInfo.Vehicle`, `InventoryEntry.Travel` and `AbilityInfo.Travel`; `MenuKind.Port`, `PointKind.Port` and `NameKind.TravelKind`.
* Developer tools ([`../docs/dev-tools.md`](../docs/dev-tools.md)): `DevIds(DevList)`, `DevWarp`, `DevWarpCell`, `DevSetFlag`, `DevGive`, `DevMoney`, `DevSetLevel`, `DevBattle`, `DevEndBattle` (the result and the round's events), `DevVehicle`, `DevEncounters`, `DevRunEvent`, `DevMark`; `WorldInfo.Dev` and `Encounters`, `SaveSummary.Dev`; `EventPosition()` (null while no event runs), `FieldZones()` (records `Zone`), `SaveText()` and `LoadText(text)`, and `Reload()`, which loads the data again behind the same `GameSession` and throws `PsivDataException` with the problems when it does not load.
* The Ashen Fells round: `EquipAt(member, piece, slot)`, `EquipPreview(member, piece, position)`, `EquipSlot.Shield` and `LeftHand` (`Native.SlotCount` 7), `ShopKind`, `AreaKind.Vessel`, `PointKind.Helm` and `Gangway`, `CellFlags.Soft` and `Barrier`; `FieldInfo.ShipPort`, `FieldPoint.ShopKind`, `Combatant.Flying`, `EquipPreview.Position`, `AlsoReplaces`, `AlsoReplacesName` and `Hands`, `InventoryEntry.CallsVehicle` and `Hands`, `ShopInfo.Kind`.
* `Create` refuses a library whose ABI version differs from the wrapper's.

The data directory is found above the binary or the working directory when `--data` is left out (first in `../Resources` beside the binary, a macOS app bundle's place for it). The asset directory (`--assets`, else `assets/` beside the data directory when there is one) replaces generated pictures and sounds with files, each optional; [`../docs/assets.md`](../docs/assets.md) documents it. F5 in the window reloads it (a key of the window's own, like F11), and `--watch-assets` reloads when its files change. `--frame-digests FILE` writes a digest of every headless frame's draws, one line each, which the round trip compares. `--battle-layout front|side` draws battles in that layout whatever the battle presentation table says (below, Battle). `--realtime` gives a scripted window the real-time field input and the window's own clock instead of 16 ms frames; `--pacing-log FILE` writes one line per drawn frame (frame, wall milliseconds since the last draw, the frame time the controller got, the leader's drawn position), for frame pacing.

With `--strict-text` a headless run fails, printing the key, when the sample asks for a key the language's table lacks.

| `PartyTalk` (party talk; on the Items page, the next sort order) | T | X |
| `TextLog` (the text log; in a battle, shows or hides its event log) | L | right trigger |
| `Skip` (an event's skip) | Tab | Back (shown as Select) |
| `PagePrev`, `PageNext` (field menu tabs, the shop's buy and sell, the status page's stats and abilities) | Left, Right | shoulder buttons, D-pad left and right |
| `Pause` (the pause overlay, in the field and a battle's command menus) | P | Back (shown as Select) |
| `FastForward` (held during a battle's playback: the round to its end at once) | F | right shoulder |
| `Interact` (the real-time field input only: as Confirm in the field) | E | - |
| `Run` (the real-time field input only: held, walks at the run speed; with Always run on, held, walks) | Left Shift | left shoulder |
| `RunToggle` (the real-time field input only: Always run on or off) | Caps Lock | left stick press |

The field has two inputs. The classic one, every script's unless it says `fieldinput realtime`, sends the held direction to the session as it is (a tap turns the leader, a hold walks a cell per `step_ms` of it) and is what every existing run plays. The real-time one, the window's when no script plays it and on `--realtime`, leads the walk itself (`SampleController.Field.cs`): a step starts on the frame a direction is wanted when its cell can be entered (the map's walkable cells on foot, what the vehicle crosses aboard, no parked vehicle or visible enemy), the leader glides from that frame over the step time, and the session is held that way on the same clock, so it puts the leader there by the time the glide ends; the frame is split where a step ends, so the next starts at once with no stop between cells. A tap walks exactly one cell. A direction pressed during a step goes next, even if let go; otherwise the latest pressed of those held goes on, and letting it go falls back to the one still held. A wall or a visible enemy gets the direction as before (a turn, a battle). Aboard, steps take `leader_step_ms`; on a running conveyor input is ignored and each carry glides over the conveyor's own `step_ms`. `Run` held (or Always run, toggled by `RunToggle` or on the options page) shortens the step to the layouts' `run_speed_percent` (200% by default; [`../docs/ui-layout.md`](../docs/ui-layout.md)) by giving the session the step's milliseconds that much faster, so play time and visible enemies run faster during a running step (the session has no run of its own). The stick snaps to four directions with hysteresis (in past half its travel, out under 0.35, the other axis taking over only when 1.3 times as strong). Confirm and `Interact` act on the faced cell, or else on a neighboring cell that answers (the sides, clockwise first, before the back), turning the leader to it first; pressed during a step they act when it ends. With the `Interaction prompt` option on (the default) the field layout's `prompt` window names the key and what it does, and the `pointer` sprite bobs over the target, while the leader stands. The two options live in `controls.json`'s `field` object (`{"always_run": false, "interact_prompt": true}`). With the real-time input on, the options page shows them before Controls and the Controls page lists `Interact`, `Run` and `RunToggle`; with it off both pages are as they were. Something across a counter cannot be reached: the session interacts only with the faced neighbor.

The mouse walks: a left click on the field walks the leader to that cell (below). F11 toggles borderless fullscreen; it is the window's own key, outside the bindings. With `--dev` the developer tools add keys of the same kind (`` ` `` console, F2 to F4 and F7 to F10 overlays, F6 data reload, F12 previewer, `[` `]` speed, `\` pause, `.` step; [`../docs/dev-tools.md`](../docs/dev-tools.md), "Keys"). Start stays on `Menu`, as before, so `Pause` takes Select, which is otherwise `Skip`: `Skip` is read only while an event runs and `Pause` only in the field and in battle, so the two never compete.

A direction tap turns the leader whichever input it comes from: it goes to the session as held input for that frame. The stick counts past half its travel, along its stronger axis only. Name entry, and naming a macro, take letters and digits from the keyboard (Backspace erases, Enter confirms, Escape cancels a macro name) or from an on-screen character grid: the directions move over it, wrapping at its edges, and the gamepad's `Confirm` button types the letter under the cursor or works the Space, Del and OK cells; the gamepad's `Back` button erases (on an empty macro name it cancels) and its `Menu` button confirms, so a gamepad alone can type. The window reads `GamePad.GetState(PlayerIndex.One)` each frame; with no gamepad, or after it disconnects, its buttons count as up, and a connect or disconnect prints a line. The controller only sees sets of keys and buttons, so headless runs need no device. Hints (the bottom line, the dialogue box, the battle menu, the field menu, the shop) name each action's first binding, from the gamepad when the last key or button that went down was on it.

Bindings live in `controls.json` in the saves directory: an object with one entry per action name, each with `keys` (MonoGame `Keys` names) and `buttons` (MonoGame `Buttons` names, the stick as `LeftThumbstickUp` and so on). The controller loads it when it starts. A missing file gives the defaults; one that does not parse, or names an unknown action, key or button, gives the defaults and logs one line. An action the file leaves out keeps its default, and `Up`, `Down`, `Left`, `Right`, `Confirm` and `Back`, which the menus need, get their default back (with a log line) when the file leaves them unbound. The options screen's Controls page lists every action with its keys and buttons and works through the controller's calls: `Controls()` (every action with its keys and buttons as display strings), `BeginCapture(action)` and `Capturing` (the next key pressed replaces the action's keys, the next button its buttons; Escape cancels; the screens get no input meanwhile), `ClearBinding(action)` (refused for the six actions above, shown as a toast), `ResetControls()` (after a confirm) and `SaveControls()` (on leaving the page).

What is drawn:

* Field: the whole window is the map, drawn in 48 px cells (16 px pictures at 3x), so 1280x720 shows about 26 by 15 cells. The camera follows the party leader, stops at the area's edges and centers an area smaller than the window. The game moves everyone a whole cell per step; the sample glides each sprite between cells over the area's `step_ms`, starting when the session reports the new cell, so the view scrolls smoothly and game timing is untouched. Tiles depend on the area kind (town: cobbles, slate roofs, plaster walls with windows; field: grass, hedges; dungeon: flagstones, rock, brick). Floors pick one of four variants and an occasional decoration (flowers, pebbles, cracks, moss, a grate) from a hash of the cell's coordinates. A wall with a non-wall cell below shows its front face, others their top, with dark edges toward open cells and a shadow on the floor under them. Water has four frames, a bank on its top edge and foam on the others. Exits on the area's edge are pulsing arrows pointing out, others a doorway; chests are closed or open (`active`), shops a stall, rests a bed, and active step hooks a faint rune. Script actors (`psiv_field_actors`) are people with four facings and a two-frame walk; hidden ones are not drawn. When a script moves one, the session reports its end cell at once and the sample walks the sprite there a cell at a time, along x and then y as the game does, one area step time per cell (divided by the move's speed), and finishes the move action when it arrives, so the event waits on the walk; anything else that changes an actor's cell (a load, a skip) puts it there at once. A script's `move` or `face` of a party member plays the same way, but the session reports nothing for it: the game keeps only the leader's cell, which scripts do not move, so where a scene puts party members is presentation (see `../game/README.md`, "Actors"). The sample follows each such action as it starts: a move walks the member from where it is drawn to the marker (or the position's x and z, rounded) and leaves it facing its last leg, a turn faces it toward a marker, an actor or another member along the longer axis, as the game turns actors. The script actors in the party's area are all in `psiv_field_actors` and every actor is in `psiv_actor_ids`, so an action whose subject is an actor outside the party's area is finished at once with nothing drawn, not even a label, and any other subject of a move, turn or `anim` is a party member. A member outside the lineup has no cell until a script's first move puts it on the marker at once (as the game puts an actor without a talk point), or a turn or `anim` that comes first puts it next to the leader: on the nearest walkable cell that no drawn person, actor or member stands on or walks to, trying the cell behind the leader (against its facing), then its right and its left, then the cell in front, and further out in the same order when those are all taken. From then on it is placed like any other member. The member stays there, out of the walking line, until the event ends. Then the leader is drawn at its own cell at once, since the player has it back; each other lineup member the scene moved walks back to its place in the line, a cell per area step, and turns the way the leader faces when it arrives; members outside the lineup are no longer drawn. The walk back takes the shortest path over walkable cells that avoids the leader, the cells other drawn members stand on or are going to and the visible actors (trying north, east, south and west from each cell, and at most six cells longer than the straight walk); only when there is none does it go along x and then y as scripted moves do. Player control is not held back: if the leader takes a step before they arrive, the trail takes each of them over from where it is drawn, gliding a step time per cell of the gap. After a skip or a load the session's instant actions (the interpreter's rebuild: each subject's last move, its later facing, its looping pose) put the members where watching left them. An `anim` plays a pose on an actor or a party member: nod (the head dips two pixels twice, tipping forward at the bottom, with a stroke beside each side of the crown), shake (the head turns to show its profile one way and the other, or toward the viewer from the side, with an arc on each side of it), jump (a hop), startle (arms up, a hop and a `!`), bow (head and shoulders lowered and held), wave (an arm up, the hand swinging), and for any other name two small bounces. `Art.PoseFor` maps script animation names to poses in one place. A pose keeps the person's facing; the event waits for one play of it (480 to 900 ms), and a looping `anim` repeats until another `anim` for that person or the end of the event and is finished at once, since the script does not wait for loops. A speech bubble waits while its actor plays a pose. A talk point named after an actor shows that actor, with a speech bubble while the point has something to say and the actor stands on it; any other talk point is a noticeboard with the bubble. A bubble is left out while the leader stands on the cell it covers. Visible enemies are creatures colored by encounter, bobbing, with a `!` while they chase. The leader is the first member of the lineup the session reports, with four facings and a two-frame walk; the other active members follow in lineup order (all four followers of a full party) in the leader's last cells. The session does not report follower positions, so follower cells are presentation only: the trail is the sample's own and starts over when the leader is moved more than one cell at once. Sprites are drawn top row first, party, actors and enemies together. A banner names the area for a moment on arrival; the area name, money and play time sit at the top, notices (party talk that comes up by itself on arrival among them) stack at the bottom left, the controls at the bottom. A left click on a cell walks the leader there with the session's `WalkTo` and `WalkStep`, a step each time the area's step time has passed, so the pace and the game time are a held direction's; a ring marks the goal, any direction, `Confirm`, `Back` or `Menu` stops the walk, and a cell with no way to it says so.
* Vehicles and ports: the party's vehicles (`psiv_field_vehicles`) stand where they were left, drawn from `Art.Vehicles` per facing with a bob (`vehicles` in the asset manifest replace them). Confirm facing one boards it (`psiv_interact`); aboard, the vehicle glides with the leader at `leader_step_ms`, the leader sits a few pixels up in the hull, the other members ride along unseen, the hint reads "drive" and "step off", and Confirm steps off (`psiv_leave_vehicle`). A click walks aboard too, at the vehicle's pace, over what it crosses. A port is a pier (the `pier` sprite), grey while closed; Confirm at an open one opens the travel screen.
* Travel screen (a port's menu, or a travelling item or technique chosen on the field menu's Items or Status page): one window as tall as its rows, centered above the toasts, titled Ferry or with the item's name, listing each destination's area and region and a Leave or Cancel row, with the highlighted row's arrival below; Confirm travels (`psiv_travel`), Back leaves. From the field menu, an item or technique with nowhere to go gets the session's refusal as a toast instead (no town in the region, inside a dungeon, outside one).
* Panels and the scene's camera: a script's `panel show ID camera CAMERA layout SLOT` puts a framed window over the dimmed field showing the live field scene (tiles, actors, the party, walks and poses still playing) as that camera sees it. A camera looks where `game.json` aims it (`psiv_cameras`): a marker of the party's area, the person (script actor or party member) it follows as it moves, or the leader. A camera with no target, or whose target is not in view (a marker of another area, a person not drawn), falls back to the marker of the same name in the party's area, else the person with that id, else the leader; a panel's view stops at the area's edges like the field's. Panels draw at the field's 48 px a cell times the camera's zoom (60 px for the placeholder's `lookout_east` at 1.25, 36 px for `lookout_front` at 0.75). Slots tile the screen above the dialogue box's band at the bottom, inside 24 px margins with 16 px gutters: `full`, `left`, `right`, `top`, `bottom`, the quarters `top_left`, `top_right`, `bottom_left`, `bottom_right`, the thirds `wide_top`, `wide_bottom`, `tall_left`, `tall_right`, and `center`. `game.json` lists the same names as layouts, so the event checker accepts exactly these; a name the sample does not know (from other data) shows as `center` with one log line. A show slides the panel in 64 px from its nearest screen edge while it fades up from black over the action's `duration` from the data (0.35 s for every panel in the placeholder, 0.5 s for the ladder panel), 350 ms when it has none, and the event waits until it is in; a hide plays it backwards; `clear` hides them all together; `instant` actions (a skip's or a load's rebuild) put the end state up at once and a cancelled one jumps to its end. `camera cut` and `camera move CAMERA SECONDS` make that camera the scene's: the field outside the panels centers on it (gliding over the move's seconds, the event waiting) and stays there until another camera action or the end of the event, and a panel showing that camera pushes in by a third over the move (48 to 64 px a cell at zoom 1); the move lasts its `duration`, which is the script's seconds unless the data gives the camera's moves another. A `shake SECONDS strength N` moves the field and every panel's view up to 10 px times the strength, easing off over its seconds; with the profile's reduced flash it moves a quarter as far. When the event ends the panels, the scene's camera and any shake go. The dialogue box goes where it covers the fewest panels, then the least of their area, else at the bottom, which with the slots above covers none at 100% text size; the area banner is left out over panels.
* Dialogue: while a line or choice is up, a bordered box at the bottom (at the top when the leader stands where it would cover them; over panels, as above), the speaker's name on a plate, a portrait from the speaker's look, wrapped text, choices with a cursor bar, skip. The text reveals at the profile's text speed (25, 50 or 100 characters a second, or all at once for Instant), wrapped as a whole first so words do not jump lines; `Confirm` shows the rest of the line, the next `Confirm` moves on. With auto-advance on, a fully shown line moves on by itself after 50 ms per character, at least a second; questions still wait for an answer.
* Battle, in one of two layouts, the battle presentation table's `layout` (per encounter or area too; `--battle-layout` and the `battlelayout` script verb override it; [`../docs/assets.md`](../docs/assets.md)). The front layout, the default: the backdrop fills the stage; the enemies stand in a row across the middle facing the camera, larger than in the side view (176 px up to three, 160 for four), from five on in two ranks (the first half in front at 136 px, the rest at 112 px further back, in the gaps), each with its label, HP bar and status icons under it; the members are seen from behind along the bottom, each over its slot in marching order (back figures, head and shoulders at 144 px), partly behind the status strip: five equal slots across the full width, each with the member's name, status icons, HP and TP numbers and bars and the command chosen (or Fallen, Defending and the statuses), an empty frame for a slot without a member, the slot of the member choosing or acting filled and framed, a targeted one's frame pulsing and a hit one flashing red (only framed red with reduced flash). The member choosing stands a little out of the line and the command window (two columns of four rows, paged past eight) opens beside it, toward the screen's middle, between the enemies' labels and the strip; the description strip stays at the top; the keys that work show in a line under the strip. In a turn the actors rise out of the line (an enemy comes toward the camera), the action's name is a framed name plate centered at the top of the stage, under the log when it is shown (a cancel's reason too, like the opening, round, notices and outcome), so it covers no party figure, effects play on the enemy row (on several targets they sweep along them, left to right), and an enemy's hit shows its effect and number over the member's head. A fallen member slumps, grey. In a vehicle battle the vehicle, seen from behind, stands left of the middle in the members' place, its own plate (name, HP and TP) above the strip's right end; the members keep their slots, and effects and numbers on them land over their slots. While the command window is open the members on its side step along past it, as close to their slots as the screen allows, so it hides no party figure. The result window sits in the middle of the stage. The side layout: a backdrop for the encounter, area or area kind (sky, hills, rooftops or a cave, and the ground tiles), the enemies on the left as figures (one row up to four, two ranks from five, the first in front; drawn back to front) with their labels, status icons and HP bars, the party on the right in a diagonal facing them, a panel per party member (portrait, status icons and names, HP and TP bars, the command already chosen) with the acting member highlighted, the pointer over the figure being targeted, and the command menu (attack, technique, skill, item, defend, escape, macro and auto). In a vehicle battle only the vehicle stands on the field, larger, at the party's middle (the members ride inside, so their panels stay but they have no figure and take no commands), and its panel shows its south field frame. In both layouts a vehicle's command menu holds only its attack, each of its skills with the uses left, and escape. The Item menu also lists the member's worn pieces that have a battle use, marked as worn, the description saying they are cast without being used up. While a technique, skill or item is highlighted, or an enemy targeted, a strip at the top shows its description. `TextLog` shows and hides the event log across the top (newest line brightest).

  Each round plays from the session's typed events (`ResolveRound`), as staged steps on the controller's clock (`BattleTimeline`): an opening banner (party or enemies first, the event's own message) and a round banner, then each turn: the actor steps forward (every participant of a combination), a retarget moves the pointer from the fallen target to the new one, a banner names the action (a combination with each participant and the ability it put in, from the round's `CommandsLocked`, since `ComboTriggered` lists only the participants), the figure's animation (attack lunges, cast and item glow), the effect on each target (group and all-target actions on every one), then the results: hurt figures shake and flash red, numbers float up (damage white, a critical larger in yellow with `!`, `Weak` orange, `Resisted` blue, `Immune` and `Miss` grey, healing green, revivals, statuses landing, resisted or ending, stat changes, items with no effect), HP and TP bars run to their new values, status icons grow in, the fallen fade (a fallen party member lies down); and the actor steps back. A cancelled action (asleep, silenced, not enough TP, no target) shows its reason in red, and takes no time for a fallen actor. An escape steps forward and says whether the party got away. After the turns, statuses that wore off blink out of their icons; then the outcome, and a won battle's result screen with experience, money, drops, and each level-up with the abilities it taught (`BattleResult`); a lost one's says the party has fallen. Notices during a battle (auto-battle on, a level-up) play as their own banners. The enemy formation changes as the events say (`EnemyJoined`, `EnemyLeft`, `EnemyTransformed`): after the turn's results, a summoned or replacing enemy joins at its formation position (the stage spreads over a new position, and its label, bar, statuses and the target list follow), an enemy merging slides into the other, which changes form, and a next form replaces the figure, label and bar at full hit points; each is a step of its own whose look comes from the table's `changes`. An instant defeat that lands stamps its mark on the enemy as it fades, with "Felled!"; resisted or immune, it floats that word. Technique points restored float as `+N TP` in the TP bar's color while the TP bar runs up. A fallen machine member standing up after the battle is a step before the outcome. Every word on the battle screen, the log lines included, comes from the text tables (`ui.battle.` keys). How each action looks (animation, effect, cue, step lengths, shake, flash) comes from the battle presentation table, with fallbacks by ability kind, effect and element for any id it does not name (see [`../docs/assets.md`](../docs/assets.md)). The battle speed scales every step (1.5x, 2x, 3x); `Confirm` finishes the current step; holding `FastForward` plays the rest of the round at once, without its cues; reduced flash leaves out the flashes and damps the shakes to a quarter. Auto-battle and macros play through the same steps. The playback only shows what the session already resolved: it changes the shown battle by each step's events as the step starts, and when a round's playback ends the shown numbers, statuses and falls must equal the session's (a difference is logged). Each step's log lines (the old playback's text, in the same order) go to the log and the headless transcript as they start, with a `present:` line naming the step.
* Field menu, one tab per page (tabs that do not fit slide with the selection, with marks where more are hidden): Status (each lineup member's level, experience and experience to the next level, HP and TP bars, every stat with its equipment bonus, critical and evasion, the weapon's element, element affinities, status resistances, each slot's piece and bonus and current statuses, scrolled with Up and Down; on its second page every ability with kind, cost and skill uses and the highlighted one's description, the field ones usable from there), Items (count, kinds, a target member when the item needs one, the highlighted item's description below the list, and the party talk action stepping the order through id, kind, name and count, `psiv_inventory_sorted`; the order is the sample's own and is not saved), Equip (member, slot, then the bag's pieces for that slot, those the member cannot wear dimmed and marked, or removing the worn one; browsing a piece shows the session's comparison, `psiv_equip_preview_get`: its description, its effects in words, who in the party can wear it, then each stat before and after and any change of element, basic attack, abilities and resistances, or why it cannot be worn; removing shows the stats before and after, and after any change the stats that moved), Save (the manual slots with area, play time, difficulty, party and write time; an occupied slot asks before it is overwritten), Order (pick a lineup member, then the one to swap with), Macros (the editor: macros with marks for the auto macro and for steps that cannot run now, new, rename, move up and down, use for auto-battle, delete after a confirm; steps with each one's issue, add, change, move, remove; a step is built member, command, ability or item, target rule, then the member or enemy position the rule needs), Combos (discovered of total, each found combination with its members, abilities and when it was found, the rest as not discovered; `Confirm` on a found one makes a macro of it named after the combination, `psiv_macro_from_combo`), Quests, Codex (titles and the selected entry's text), Log (the newest lines first, Up for older ones) and Options. Every list scrolls with a scroll bar when it is longer than its box. Shop (buy and sell, the highlighted entry's description, and for a piece its bonuses and who in the party can wear it), inn, save prompt (the shared slot list), name entry (with its grid), quest log and text log: one window style over the dimmed field.
* Title: a field scene behind the menu: Retry the battle (after a game over that offers it), New game, Continue, Load (every save, manual slots first, then the autosaves, with the same summaries; a damaged save shows its error and does not load), Sound test (once the save directory holds a clear-data record: every audio id of the data by its `ui.track.*` title, Confirm plays one, Back returns to the title's music), Options and Quit.
* Options (from the title, the pause overlay or the field menu's Options tab): text speed, auto-advance, text size (100% to 150% in steps of 10), battle speed, reduced flash, ambient party talk, shipped or restored names, text language (the game's languages), music, ambient and effects volume (applied at once, see "Audio"), difficulty (stepped through the session's presets, `psiv_difficulties`, with the preset's description saying what it changes, while a game is in progress outside battle; shown only otherwise) and reward multiplier (stepped under the same rule), each with a line saying what it changes; Left and Right or `Confirm` step the value, and the session's refusals show as toasts. Then the Controls page.
* The window: the controller draws a frame at the layout's logical resolution (1280x720 by default), which goes into the window centered with black bars, scaled by the largest whole number that fits (1x in a 1920x1080 window, 2x in 2560x1440) so the pixel art stays sharp, or shrunk to fit a smaller window (`Letterbox`); the layout's styles can ask for whole numbers only, any factor, and a safe area ([`../docs/ui-layout.md`](../docs/ui-layout.md)). The window can be resized; F11 toggles borderless fullscreen; mouse clicks are mapped back through the same box. `--window-size WxH` and `--fullscreen` start it that way.
* Pause, over the field or a battle's command menu: Resume, Options, Quit to title (after a confirm). The session gets no updates while it is up, so play time stops.
* Text size scales the text of dialogue, the title, the menus, the logs, options, pause, shop, inn, the save prompt and name entry, and their row spacing; the field, its HUD and the battle screen keep their size. Reduced flash damps a script's shakes and the battle's to a quarter and leaves out the battle's flashes, the only flashing effect the sample draws. A text language change shows at once, since every screen reads its text from the session each frame.

Every picture is generated by `Art` from code unless the asset directory names a file for it: palettes, a few 16x16 character templates (people, creatures), procedural tiles from a seeded generator, battle backdrops, figures and effects. Every person, party member or actor, looks the same in the field, the dialogue portrait and the battle panel: hair, skin, coat and scarf colors, headwear (none, a cap, a hood, long hair or a headband) and clothes (a coat, an apron or a belt) all come from a hash of its id. Creature colors and horns come from a hash of the encounter or enemy id.

The sample plays script actions with the asynchronous presenter (`Presentation.Wait`): each action becomes a timed animation and the controller calls `FinishAction` when it ends, so events wait on them. A move, turn or `anim` of a script actor or a party member plays on its sprite as above; a fade darkens or clears the screen over its seconds held between 150 and 600 ms; panels, cameras and shakes play as above for their own lengths; music, ambient and sound start at once (a music fade waits its seconds), as "Audio" says; a warp is done at once, the new area's banner showing the arrival. Only an action the sample has no picture for still slides a label with its subject across the top: a `show` or `hide` of a party member, a move or turn of an actor not drawn yet, and a party member's move or turn toward something not in the area. Since every action shows on screen, the session's action notices (`(face dockhand dock_front)` and the like) do not become toasts; they stay in the headless transcript as `notice:` lines. Other notices (arrivals, autosaves, items, shop results, refusals) still show as toasts. Animations, the dialogue's reveal and auto-advance and the battle's playback advance by the frame time the controller gets, so headless runs, at a fixed 16 ms per frame, stay deterministic. A direction tap goes to the session as held input for one frame; the game turns the leader at its next tick.

Text is drawn with FontStashSharp from the first system font found in a fallback list (Arial, Verdana, Geneva on macOS; DejaVu, Liberation, Noto on Linux; Segoe UI, Arial, Tahoma on Windows; CJK faces after them as fallbacks for missing glyphs). `--font FILE` or `PSIV_FONT` puts a font first.

### Replacing the drawing

The sample keeps the game out of its drawing code: `SampleController` reads the session after each update and draws through `IDrawSurface` (`Fill` a rectangle, draw `Text`, `Measure` text, `CreateImage` from a pixel array and draw it scaled with `Image`, `Clip` to a rectangle and `Unclip`, which panels use, `ReadImage` a PNG, `ClearImages` before a reload, `UseFont` for the UI skin's fonts, `UseBitmapFont` for the asset directory's bitmap fonts, whose glyphs the surface draws as images with the font `UseFont` set filling in the ones a font lacks). `MonoGameSurface` implements it with a `SpriteBatch`, one texture per image, `Texture2D.FromStream` and FontStashSharp; `RecordingSurface` is the headless one, which checks image handles and sizes, counts draws, folds each frame's draws into a digest (pictures by a hash of their pixels) and needs no graphics device; `CanvasSurface` draws into a pixel buffer (the export, the generated backdrops). The asset directory is the first way to put real art behind the same screens (`../docs/assets.md`). Animation runs on a clock that advances only by the frame times the controller gets, so headless runs stay deterministic. To put real art behind the same screens, change what `Art` hands the surface (load sprite sheets instead of generating pixels), implement `IDrawSurface` over another renderer, or replace a screen's `Draw*` method and keep its `Update*` method, which holds all the session calls; each screen's pair is in its own `SampleController.<Screen>.cs` file. For a real game, keep the frame loop of the section above and write the screens from scratch: everything they need comes from the records `GameSession` returns, and animations hook in through `Presentation.Wait` and `FinishAction`.

### Audio

Everything the sample plays goes through `IAudioOut` (`Audio.cs`): `PlayMusic(track, fadeMs)` (one track at a time; the next fades in while the last fades out), `StopMusic(fadeMs)`, `PlayAmbient(sound, fadeMs)` and `StopAmbient(fadeMs)` (one loop), `PlayCue(cue)` (one-shot), `SetVolumes(music, ambient, effects)` and `Update(dtMs)`, with `Music` and `Ambient` saying what plays. `RecordingAudio` is silent and logs every call, which headless runs assert on (`expect audio`); `MonoGameAudio` keeps the same state and log and plays through `SoundEffect` instances, looped for music and ambient, with each group's volume times its fade.

Unless the asset directory names a file for an id (WAV or Ogg Vorbis, with loop points and a gain; see `../docs/assets.md`), `Synth` generates the sound: 16-bit mono PCM at 22050 Hz in code, as `Art` does pictures: sine, square, pulse, triangle, saw and filtered noise, note envelopes, glides and a step sequencer. A track is an eight-bar loop of sixteen steps: a lead walking a scale and landing on chord tones, a bass on the chord roots, an arpeggio and noise drums, its tempo, scale, root, chords, patterns and lead waveform drawn from a hash of the id, its mood from the id's prefix (`battle`, `dungeon_`, `town_`, `title`). An ambient loop (four seconds, end blended into start) is wind, surf, drips or a hum by the hash. Any cue id gets two to four hashed tones; the sample's own cues are shaped in one table. So every id a script names sounds different with nothing authored per id, and the table overrides the ones the sample uses. Cues are generated when the window starts, tracks and loops the first time each plays; every buffer is normalized to 70% of full scale.

What plays:

* Music, from the data first (`psiv_game_info`'s title, victory and defeat tracks, `psiv_battle_info`'s encounter track, `psiv_field_info`'s area track): the title's track at the title; a script's track from `music play` until the event ends (`music stop` and `music fade` silence it until then); otherwise during a battle the encounter's track, the victory track on a won battle's result screen and the defeat track on a game over's; otherwise the area's track, which comes back after a battle and when an event ends. Where the data names none the ids are derived as before: `title`, `battle_<kind>` (`battle_town`, `battle_field`, `battle_dungeon`) for visible and random battles and `battle_scripted` for an event's battle, nothing on a result screen, and `<kind>_<area>` (`town_tidewater`). Changes crossfade over 800 ms. The placeholder names a track for every area, the title, victory, defeat and the marsh and warden encounters; the training encounter's battles still use the derived ids.
* Ambient: a script's `ambient play` loop until `ambient stop` or the end of the event; none otherwise.
* Script audio actions: `music play` and the ambient actions are done at once, `music fade` when its seconds are up, `sound` plays its cue and is done at once. `instant` ones (the rebuild after a skip or a load) switch without a fade, so loading the autosave before a scene's battle brings back the scene's music and wind; a skip issues no sounds (the interpreter drops them) and leaves music and ambient where the scene left them.
* Cues (`Synth`'s table): `cursor` (a direction on a menu, the title, a choice or a battle menu), `confirm`, `back`, `refuse` (a refusal the session reports; it replaces the confirm), `menu_open` and `menu_close` (into and out of any menu, shop, inn, log, options, pause or load screen), `text` (while a line reveals, at most one per 70 ms), `line` (a line moved on), `save` (a manual save), `step` (the leader's step in the field, at most one per 200 ms), `battle_start`, and from the battle's events as the steps that show them start, mapped in `SampleController.BattleCue`, with a presentation table entry's own cue at its effect: `hit` (damage), `miss`, `critical`, `heal` (healed or revived), `status` (a status or stat change landing), `enemy_down` (an enemy falls), `victory`, `game_over`, and `level_up` from the level-up notice.
* Volumes: the profile's music, ambient and effects volumes, read every frame, so a change in Options applies at once.

Devices: headless runs always use `RecordingAudio`. The window uses `MonoGameAudio` unless `--mute` is given; when MonoGame cannot open an audio device (CI, Xvfb, containers, `ALSOFT_DRIVERS` naming no backend) the window logs one `audio: no device (...)` line and runs with `RecordingAudio`, and a device lost later logs one line and goes silent. `--dump-audio DIR` writes `music_town_tidewater.wav`, `cue_confirm.wav`, `cue_hit.wav` and `cue_level_up.wav` and runs the self-check.
