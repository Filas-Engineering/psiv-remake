# game

A headless game session library that joins the battle rules (`../core`, namespace `rules`) and the event interpreter (`../events`, namespace `events`) into something playable, plus a terminal front end and a small original placeholder adventure. Plain C++17, standard library only, no exceptions across the public API, integer rules arithmetic. Namespace `game`.

## Checking data

`game_cli --check DIR [--core DIR]` (`checkData` in `check.h`) loads a data directory the way the game does, with `loadGameDataPartly`, which keeps whatever loaded and goes on reading the game's own files when the battle data has problems. It prints every problem as `file:line: text` (a path you can open; line 0 or none when the problem is about a whole file or a table key), then counts of what loaded (core: statuses, abilities, items, equipment, characters, vehicles, enemies, encounters, combos, difficulties, macros, text keys; game: areas, markers, exits, hooks, shops, rest points, chests, zones, scripts, events, flags, variables, actors, prices and journal entries; per language: game text keys, descriptions and dialogue strings), and exits 1 on any problem. When problems stop the load before the scripts are compiled, it says which checks did not run.

The loader's own checks include the presentation data (a camera's marker must exist in its area, a followed id must be an actor or a character, every music id must be one of `presentation.audio`, music may name only encounters the battle data has, durations name known actions) and the descriptions (a `desc.*` key must name a kind and an id the battle data has; a missing description is no problem). On top of them, `crossCheck` reports: two solid things (interact hooks, shops, rest points, chests, ports, and the cells actors stand on apart from a talk point: an interact hook's `actor_at` and a solid `game.json` home) on one cell; a marker, exit, step hook or spawn point on a solid cell; a hook id or zone id used twice in an area, or a chest id used in two areas; a zone with `from` past `to`, reaching off the map, or overlapping another; a shop with nothing in stock; exits, markers, step hooks and solid things used from beside them (points: everything but an actor's own cell) the party cannot walk to (or stand beside, an exit or gangway cell not counting, since standing there leaves the area) from any marker an exit, a script warp or the start leads to, walking only on floor (in a `field` area also over terrain a vehicle of `game.json` crosses) and never through another exit (a way in on an exit cell is a starting point the walk leaves from, since arriving there does not take the exit; R150), a platform's docks joined (R129), a door's exit cell crossable (R145), an interact hook with `solid: "while_active"` counting as passable when its flags (`require_flag`, `block_flag`) or its actor (a `game.json` actor, which scripts show and hide) can switch it off (such a hook may stand aside, so a thing behind it is reached in that state; the hook itself is used while it stands, from the first cell beside it a walk reaches, which never needs a way through it), and one without flags or an actor, which can never switch off, blocking like any solid thing, an actor's own cell always blocking (`Solid::point` in `src/check.cpp` tells points from cells that only block), a thing used under the interaction rules in effect ([Interaction](#interaction): an interact hook from beside any of its `cells`, a hook with `across` or every point under `interact_across` also from the cell beyond a counter straight ahead, a counter being a cell of the map as written that is not floor and holds nothing solid and no exit, and under `interact: "nearby"` a talk point with `actor_at` also from beside its actor's cell; `Use` in `src/check.cpp`), ports' markers and towns' arrival markers counting as ways in; an area nothing leads into, or one the start area cannot reach through exits (a script warp's target counts as reached, and any port's area once another port's is). When the loader did not get as far as its references, `crossCheck` also checks exit targets and every language's `area.<id>`. Area problems from the loader's own reference check also carry the area file and line. [`docs/data-import.md`](../docs/data-import.md) is the guide for a team converting its own data.

## How an engine drives a frame

The engine owns one `GameData` (loaded once) and one `Session`. Every frame:

1. Call `session.update(dtMs, input)`. In Field, `input` is the held direction; the field runs in fixed ticks (`tick_ms`), moving the leader one cell per `step_ms` of held input, ticking visible enemies, and starting battles and events. A direction pressed and released between two ticks is kept until the next tick, which plays it as held once, so a tap turns the leader. In Event it steps the interpreter. Battle and Title ignore it.
2. Read `session.mode()` and present that mode:
   * Field: `world()` (position, facing, `enemies`), `area()` and `actorsHere()` (see [Actors](#actors)). Interact with `interact()`, and draw a prompt from `interactTarget()`, what it would act on now (see [Interaction](#interaction)); turn in place with `face()`; `canStep(direction)` says whether a step would move the leader now and `leaderStepMs(running)` how long it takes, and `fieldMotion()` the step's progress, the belt's step and progress and a four-direction step mask, for a host that moves the leader smoothly; `interactAt(cell)` says what stands on a cell and whether the leader can use it from where it stands; `backgroundEvents()` lists the background events running; FieldInput's `running` is the run input; open the menu with `openMenu()`, party talk with `partyTalk()`. Vehicles: `vehiclesHere()` (the party's vehicles in the area, the ridden one marked), `riding()` (its field rules, or null on foot), `board()` (the vehicle ahead; `interact()` does the same) and `leaveVehicle()`; aboard, the leader moves at the vehicle's speed over what it crosses. To walk to a cell along the shortest path, `beginWalk(goal)` and then `walkStep(walk)` until it returns anything but `Walking`, running events and battles in between; it stops at the goal, on leaving the area, when the field does not come back, without a path or after 4000 steps.
   * Event: `line()` is the pending line as data (`LineView`: speaker id, speaker name, text ID, rendered text with name tokens resolved for the profile, portrait), or empty; `lineText()` is the same as "Speaker: text". Call `confirmLine()` on the button. `choiceView()` is the pending choice (`ChoiceView`: rendered prompt and options; an ask's options are the dialogue table's `choice.yes` and `choice.no`); call `choose(index)`. `canSkip()` and `skip()` drive skipping; skipped lines go to `textLog()`.
   * Battle: `battle()` is the live `rules::Battle`. Set commands with `setCommand` (its refusal is core's message) or `applyMacro` (with `rules::MacroFallback::Automatic`, a member whose step cannot run takes core's automatic choice for the round; the terminal's `fight` plays that way). For auto-battle call `startAuto()` once, then `fillFromAuto()` at each command phase until it returns false (the stop reason is in the output). `fillFromPolicy()` is core's simple policy, and `fillAutoRound()` fills a round the way the terminal plays (the save's auto macro from the first round, then the policy). Then `resolveRound()`, which returns the round's core events for playback. `playBattle()` plays a whole battle with `fillAutoRound` and `resolveRound` and returns each round's output and events. The battle ends inside `resolveRound()`: rewards, level-ups, grace period, and the return to Field, Event or (game over) Title happen there. `endedBattle()` then keeps the battle as it ended (final combatants, outcome, record, the rewards paid out, drops and level-ups) until the next battle starts, `dismissBattle()`, a new game, a load or `quitToTitle()`.
   * Menu and Shop: `menuKind()` says field menu, inn, save prompt, name entry, port or credits. While credits play, `credits()` (`CreditsView`: id, music, entries with kind, text key, text, gap and pause, how many have come up and the play time through them) is what to draw; `update()` moves them on and `closeMenu()` says they finished. At a port (`port()`), `travelDestinations(TravelKind::Port)` lists the other open ports and `travel(TravelKind::Port, id)` goes there. From the field menu, `travelDestinations(TravelKind::Town)` and `(TravelKind::DungeonExit)` list where a return to a town or the way out of a dungeon leads, and `travel(kind, id, user, thing)` goes there with an item or a technique whose travel effect matches (`useItem` and `useAbility` refuse those with `game.refuse.travel_item`). `shop()`, `inn()`, `buy`, `sell`, `rest`, `useItem`, `useAbility`, `equip`, `unequip`, `saveManual`, `enterName`, `closeMenu`. A shop, save prompt or name entry an event opened closes back to the event. From the field menu also: `swapLineup` (party order), the macro editor (`createMacro`, `renameMacro`, `deleteMacro`, `moveMacro`, `setMacroStep`, `removeMacroStep`, `moveMacroStep`, and `macroFromCombo` for "make macro" on a combo log entry), and for status screens `memberDetail(member)`.
   * Any time: `macroViews()` (every macro with its steps, names and the reason a step cannot run now), `comboLog()` (entries joined with their recipes; `data().db.combos` counts the locked ones), `equipPreview(member, piece)` (a piece compared on a member before it goes on, held or not, so shops can use it too: its effects, who in the lineup can wear it, and the member's battle numbers before and after), `bag(order)` (items and pieces listed in an `ItemSort` order), `description(kind, id)` (an item's, piece's, ability's, status's, enemy's or difficulty's description in the profile's language, empty when none), `difficulties()` and `canChangeSettings()`.
   * Title: `newGame`, `continueGame`, `load`, `retryBattle`.
   * Any time: `questLog()`, `encyclopedia()`, `textLog()`, `profile()` and `setProfile()`, `setSettings()` and `setAutoMacro()`.
3. Drain `drainOutput()`. Each `Output` has a text key with parameters (`message`) and its rendering in the profile's language (`text`); warnings about broken data have no key. `OutputKind::Ambient` is a party talk line that came up by itself on arrival (FLD-073): show it without stopping play.

Every operation that can refuse (`newGame`, `walk`, `interact`, `buy`, `saveManual`, `setProfile` and the rest) returns a `rules::Message`: empty when it ran, otherwise a text key (`game.refuse.*`, or core's key for a battle command, field use or equipment refusal) and its parameters. `render(message)` shows it in the profile's language.

Presentation-only script actions (moves, cameras, panels, audio, fades) go to the session's own action queue, which `SessionOptions::presentation` sets up. With `Presentation::Instant` (the default) every action is done when it starts, which the terminal and the tests need. With `Presentation::Queued` the event waits on each action until the engine calls `finishAction(handle)`, so a renderer can play animations of real length. Either way `pollActions()` hands out each action once (`PresentedAction`: handle, `Begin` or `Cancel`, the action, its script text and `seconds`, how long it lasts by the data's durations; Instant keeps the last 256), and `SessionOptions::onAction` is also called as each is queued. An action with `instant` set (the rebuild after a skip or a restore) is done at once: put its end state up. `Cancel` names an action a skip abandoned. An engine with its own scheduling can pass its own `Presenter` instead. Warps change the world before the queue sees them. The terminal front end is only `Runner` plus `game_cli.cpp`; an engine replaces both and keeps everything else.

## Actors

`game.json` lists the script actors that are not characters (`actors`). An interact hook whose id is an actor's is that actor's talk point: the actor stands there, visible and facing south, until a script moves, turns, shows or hides it. A talk point with `actor_at` puts the actor on that cell instead (a keeper behind a counter): it is drawn and scripted there while the party still talks to the hook's cell. An actor written as an object in `game.json` may instead have a home without a talk point (`area` and `at`, facing `facing`), and a figure: `sprite` `{"enemy": id}` draws it with that enemy's field figure (it never fights) and `{"look": name}` names one the host knows. `actorsHere()` gives the actors in the party's area as `ActorView` (id, cell, facing, visible, whether a script has touched it, whether it blocks its cell now, how it vanished, the animation playing with its milliseconds left and in all, its removal and its figure), hidden and removed ones included, in `game.json` order.

The session follows the end state of every script `move`, `place`, `face`, `show`, `hide`, timed `anim` and `remove` of one of these actors in `World::actors`, which the save keeps (the `actors` chunk), mid-event saves included:

* The first command for an actor starts from its home in the party's area (its talk point, `actor_at` or `game.json` home), if it has one there; otherwise it has no cell until a move or place gives it one.
* `move` puts the actor in the party's area, on the marker, or on the cell of a position's x and z, rounded. It walks along x, then along y, to each `via` marker in turn and then to the target; with `pathfind` each leg goes the shortest way over floor nothing stands on, around solid actors and never through an exit (north first among equal ways), and straight when there is none. It ends facing its last step. The record of the action (`PresentedAction::route`) lists the cells, from where it stood to where it ends.
* `place` puts it on the cell at once, facing `facing` if given (its route is that one cell).
* `face` turns it toward a direction (north, east, south, west), a marker, a character (party members walk with the leader, so the leader's cell) or another actor in the area, along the longer axis; a tie turns it north or south. Nothing happens when the target is on its cell or not in the area.
* `show` and `hide` set whether it is visible and end any animation.
* `anim` with a standard animation that shows or hides (`fade_in`; `fade_out`, `dissolve`, `blink_out`) sets visible at once and records how a hidden actor vanished (`ActorVanish`). An animation that lasts (the data's seconds, a standard one's own, or `durations`) is kept with its milliseconds, which run down with field ticks and event time until it ends; a looping animation, and one of no length that shows or hides nothing, are the front end's.
* `remove` hides it, stops it blocking and its talk point answering, and ignores every later command for it: for good, or `until reload`, which ends the next time the party enters an area (any warp or exit, the same area too). Both are saved.
* An actor keeps its place when the party leaves the area, so its talk point elsewhere stands empty until a script moves it back.

The state changes when the action starts, so a renderer with Queued presentation animates from where it last drew the actor to the cell `actorsHere()` reports (along the record's route), draws a fade at the animation's milliseconds left, and finishes the action when it arrives. Skips and restores reach the same state through the interpreter's instant actions; a skip puts animations at their end state (nothing playing). A solid actor (a `game.json` home with `solid`, the default, or a talk point with `actor_at`) blocks the party's walking and paths on the cell it stands on while it is shown and not removed; other actors are presentation and do not block, and talking still goes through the hook's cell. Characters named as subjects are left to the front end.

Party members are not tracked. The world keeps one place for the party, the leader's cell (`World::position`), which only the player's walking and warps change; a script's `move` or `face` of a character changes nothing in the world (a `face` toward a character turns toward the leader's cell, above). Where a scene puts party members is therefore the front end's presentation, like the formation behind the leader, and lasts until the event ends, when the party stands at the leader's cell again. A front end that shows it follows the actions as they start, and after a skip or a restore it gets them back from the interpreter's instant rebuild, which issues each subject's last move, then its facing if a `face` came after that move, and its looping animation (`events/README.md`, the save contract). As for an actor, a facing that only a move's last leg set is not in the rebuild, so after a skip or a restore it follows from where the member stood when the rebuild ran; a scene that ends a move with a `face` comes back exactly. The MonoGame sample does this (`../bindings/README.md`, "The sample").

### Wandering actors, looks and visible enemies

An actor written as an object with a home may also `wander` (`ActorWander`): `{"radius": 2}` (cells along x plus along y from its home) or `{"from": [x, y], "to": [x, y]}` (a rectangle), with optional `speed_percent` (1 to 1000, default 50: against the area's step time), `pause_ms` (`[least, most]`, default `[1000, 3000]`: how long it stands after each step, drawn from the encounter stream when the two differ) `terrain` (the map characters it may stand on, default `"."`), `stand_percent` (0 to 100, default 0: the chance that a turn is spent standing, drawn from the encounter stream before the direction and only when above 0; a standing turn takes the pause as a step does) and `axis` (`both`, the default, `x` or `y`: the direction is drawn from east and west, or north and south, only). It walks a cell at a time from the field ticks, after the leader's step and before the visible enemies, the way visible enemies wander: it turns a direction drawn from the encounter stream and steps unless the cell is outside the map or its terrain, closed, a point, an exit or a gangway, or holds the leader, a visible enemy, a vehicle or another shown actor; outside its region (a script moved it) it takes only steps that bring it nearer its home. It stands still while it is hidden or removed, outside its home area, while a running background event has commanded it, and whenever the field does not tick (events, dialogue, menus, battles). Its progress and pause are saved with its place (the actors chunk's `wander` lines); `ActorView::wanders` says it wanders now. A wanderer is solid by default, so the leader bumps into it; a `touch` hook (see [Areas](#areas)) fires its event when the leader walks into it, when it walks into the leader, or when the leader interacts with it (an `actor` target), which is how "wander, then talk" is written. No visible enemy steps onto the cell of a shown wanderer that blocks (R121); a wanderer does not chase them. No seeded golden changed, so this needs no option.

### Patrols and paths

An actor with a home may instead `patrol` (`ActorPatrol`, never with `wander` or `path`): `{"steps": [...], "speed_percent": 50, "terrain": "."}`, a loop of entries, each `{"walk": "north", "count": 3}` (cells one way, count default 1), `{"to": "marker"}` or `{"to": [x, y]}` (along x, then along y, as an unpathed `move` goes), each with an optional `face` and `pause_ms` after its walk, or only a `face` or a `pause_ms`. It walks a cell per step time at `speed_percent` of the area's step time, from the field ticks after the wanderers, over the cells a wanderer may enter on its `terrain`; a cell that is taken (an actor, a visible enemy, a vehicle, a point or exit, a footprint, the leader) makes it wait and try again at its next step, and walking into the leader fires its `touch` hook as a wanderer does. It stands still whenever the field does not tick (events, dialogue, menus, battles), while hidden, removed, outside its home area or commanded by a running background event; a script that moves it leaves it to go on from where it stands. Its entry, the cells of that entry walked, its progress and pause are saved (actors chunk `patrol` and `wander` lines). The loader walks one round on the map as written and reports a step off the map or its terrain (`data.patrol_blocked`), a round that does not come back to where it started (`data.patrol_not_a_loop`) and a marker the home area lacks (`data.patrol_marker_missing`). `ActorView::patrols` says it walks its patrol now.

An actor with a home may instead follow a `path` (`ActorPath`, never with `wander` or `patrol`), for large or free-moving actors that are not cell-bound: `{"offsets": [[dx, dy], ...], "ticks": 1, "footprint": [w, h]}`, pixel offsets from its home (the cell's top left, at `game.json`'s `cell_pixels`, default 16), one entry per `ticks` field ticks, looping, deterministic. `ActorView::onPath`, `home`, `pathX`, `pathY` report it (draw it at home times the cell size plus the offset; `cell` is the cell holding that point). The rule for blocking: without a `footprint` it blocks nothing (whatever `solid` says); with one (1 to 16 cells each way, `footprintWidth`, `footprintHeight`) and `solid` it blocks every cell the footprint rectangle overlaps at the current offset, for walking, wanderers, patrols and visible enemies; a footprint that moves onto the leader does not push it, and the leader may step off. The data check leaves path actors out of its solid cells, since they move. The tick is saved (actors chunk `path` lines).

A script's `look` (`../events/FORMAT.md`, "Actors") replaces the actor's figure: `ActorView::spriteEnemy` or `look` then report it, `look ... default` brings back `game.json`'s, and the save keeps it (`look` lines). `show` and `hide` `with` an animation play it as the transition: the animation and its milliseconds are recorded as for an `anim`, and a hide with `fade_out`, `dissolve` or `blink_out` records how the actor vanished.

A visible enemy is addressed in scripts as `enemy.<zone>.<n>`, the n-th of that zone's visible enemies still in the field, in spawn order (`Session::enemyActor(id)` gives an enemy's name; the registry lists one per place of each zone's `cap`). `move` and `place` put it on the cell (along its route; it then wanders, leashed, from there, idle), `face` turns it, and `remove` (either form) takes it off the field without a battle until the area's visible enemies next spawn. `anim`, `show` and `hide` go to the host only, and `look` refuses it. Nothing new is saved: the world chunk keeps visible enemies.

## Story pictures and the scene camera

* Pictures (R117): scripts' `picture show`, `picture hide [NAME]` and `picture clear` change `World::pictures`, an ordered stack (a hide by name takes the upper copy of that name; a hide without one the top). The stack is game state: it applies while skipping, stays through lines, the event's end and area changes, and the save keeps it (world chunk `picture` lines). A host draws `pictures()` bottom first.
* Scene camera (R118): a `camera to` (a marker of the party's area or a cell) holds the scene camera on that cell, and `camera reset` sends it back to the leader, each over the action's seconds (the data's `durations` for `camera_to` and `camera_reset` win, as for any action). `sceneCamera()` (`World::SceneCamera`: `held`, `cell`, `ms` left and `totalMs`) follows the action as it starts; field ticks and event time run `ms` down, as they run actors' animations. Instant actions (a skip's or a restore's rebuild) land at once. Entering an area puts the camera back on the leader. The save keeps it mid-move (world chunk line `scene_camera HELD X Y MS TOTAL`, written while held or moving); loading such a save in the field goes on with the time left, and loading one in an event lands at the goal, since the interpreter's rebuild is instant. A goal outside the area warns and changes nothing. Camera cuts and moves to named cameras are unchanged (`cameras()`).

## Background events

An event marked `background` (`../events/FORMAT.md`, "Background events") runs beside the field: a hook whose event is a background one (any trigger) and a script's `spawn` start it, and the player keeps control. The rules this library gives them:

* Order: each running background event steps once per field tick, in the order they started, after the leader's step, the wandering actors and the visible enemies, by the tick's milliseconds; one spawned during a tick takes its first step at the next. Everything is deterministic from the seed.
* Pause: they step only in field ticks, so a foreground event (dialogue included), a menu, a shop, a rest and a battle pause them where they stand; nothing is cancelled. Their actors keep the end states the actions gave them.
* Stop: entering an area (any exit, warp, travel or load of another game) stops every one of them, with the host told to cancel what was in flight. A background event that ends, or stops with a runtime error (a warning), is dropped.
* Limit: `game.json` `background_limit` (default 4). A spawn past it is dropped with a warning; a spawn of one that already runs is ignored.
* Output: each action shows as `Action` output `<event>: <action>`, `spawn <event>` when one starts, `<event>: end` when it ends and `<event>: stopped` when an area entry stops it.
* Flags: a background event that changes a flag lets the field settle after the tick, so flag hooks fire as after an event.
* Saves: `SaveFile::background` holds each one's interpreter state; the `background` chunk 1 is written only while one runs. A load resumes them; a save made with other scripts starts each from its first command over the loaded world (the host gives no event-start world for them).
* A hook firing a background event does not stop the field: a load or flag hook goes on to the next hook, a step hook to the step's encounter roll.

## Interaction

`interact()` acts on what `interactTarget()` names (`InteractTarget`: an `InteractKind` (`vehicle`, `port`, `helm`, `talk` for an interact hook that is no actor's, `actor`, `chest`, `shop`, `rest`), the id, the cell acted on, the direction the leader faces to use it, `ready` (false when interact would refuse: a hook whose flags do not hold or whose actor is removed, a closed shop or port) and `across`), turning the leader to that direction first. It is empty outside the field, without player control, aboard a vehicle and when nothing answers. How it finds the target, all of it data with today's rule as the default:

* The cell the leader faces, as before. When nothing stands there and it is a counter (a cell that is not floor and holds no point, exit or solid actor), the cell beyond it, if what stands there is used across: an interact hook with `across: true`, or anything under `game.json`'s `interact_across`.
* With `game.json`'s `interact: "nearby"` (default `faced`), when the faced cell gives nothing, the first other neighbor that answers and would not refuse, in the order right of the facing, left of it, behind (each with its counter rule); and an actor with a talk point in the area answers on the cell it stands on (moved by a script, or behind its counter with `actor_at`) as its talk point does. A neighbor that would refuse is passed by; faced, it refuses as before.
* An interact hook with `cells` covers those cells besides `at` (a long table): each is solid and answers as the hook, from any side.
* An actor with a `touch` hook whose flags hold answers where it stands, as an `actor` target, under either rule.
* A marked counter (R109: a map `=` cell, or one the area's `counters` lists) that holds nothing itself passes interaction to the cell directly behind it in the facing direction, under either rule and without `across`: an interact hook, shop, rest point, chest or port there is used as if faced, and a shop's or rest point's `keeper` standing there opens that shop or rest point (its target names the shop's own cell and its keeper). The target query reports it with `across`, `interactAt` answers for the cell behind, and the data check counts a point there as reached from the floor cell two away across the counter. The older rule (any non-floor cell with nothing on it, for points with `across` or under `interact_across`) still holds where no counter is marked.

`interactAt(cell)` answers "what is on that cell, and can I use it from here": the target interact would act on once the leader faced that way (a neighbor, the cell beyond a counter, or an actor standing there), with that facing, or nothing. A shop's or rest point's optional `keeper` (an actor of `game.json`) comes with its target (`InteractTarget::keeper`) for a host to turn toward or animate.

The data check judges reach by the same rules (see [Checking data](#checking-data)). Arrival notices (R107): `game.json`'s `arrive_notice` (`always`, the default; `walked`, only when the party walks in through an exit or off a ship's gangway, not after a script's warp, travel, boarding a ship, a load or the new game's start; `never`) and an area's own `arrive_notice: false` decide whether entering an area emits `game.arrive`; `Session::arrivalAnnounced()` (C `psiv_field_info.announce_arrival`, C# `FieldInfo.AnnounceArrival`) says it for the last entry, so a host shows its banner by the same rule.

Step timing (R108): with `game.json`'s `step_timing` `exact` (default `ticks`) the leader's steps (on foot, running and aboard), the belts and wandering actors keep the time past each step and carry it into the next, to the microsecond, so a step time that is not a whole number of ticks, or has a fraction, is kept on average over any distance; the field still moves on ticks and the time not yet a whole tick carries between update calls, so one long update and many short ones leave everyone on the same cells (a step shorter than a tick still takes one). Saves keep the carry (world chunk lines `step_carry`, `conveyor_carry` and `tick_carry`, written only when not 0 under `exact`). `FieldMotion` and the C API's field info report the step times and progress in microseconds too (`stepUs`, `runStepUs`, `stepProgressUs`, `conveyorStepUs`, `conveyorProgressUs`). With `ticks` a step ends at the first tick at or past its time and the rest is dropped, as before, so data with whole-millisecond steps plays as it did. Visible enemies take the same rule (R122): under `exact` a cell costs them the area's step time to the hundredth of a millisecond (with its fraction) and the rest carries in their progress, as wanderers do; they still step only on ticks. `FieldMotion::nextTickUs` (the update time until the next tick, when a step can start or land) and `stepLandsInUs` / `runStepLandsInUs` (until the tick on which the step under way, or one started now, lands with the input held) let a host glide the leader so it arrives as the session moves it, instead of waiting for a tick at the end of each cell. The tick length is `game.json`'s `tick_ms` (one per game; areas have none), reported as `psiv_game_info.tick_ms`.

Running: with `game.json`'s `run_speed_percent` (101 to 1000; none by default, so nothing runs), the leader on foot crosses a cell in `step_ms * 100 / run_speed_percent` while FieldInput's `running` is held, or while it is not with the profile's `always_run`; aboard, the vehicle's speed holds. Running changes no step count, encounter roll or visible enemy's speed, and adds no play time: play time and visible enemies follow the field ticks, whatever the leader's speed.

## Capabilities

`game_cli --capabilities` (also C `psiv_capabilities()` and C# `GameSession.Capabilities`, the same text) prints what this build supports as one JSON object, keys always in this order, so a tool can diff two builds. `capabilities_schema` (now 1, `game::kCapabilitiesSchema`) changes when a key below is renamed, removed or changes meaning; new keys may be added without a bump.

* `capabilities_schema`: the number above.
* `versions`: `library` (`game::kLibraryVersion`, the bindings' version), `abi` (`PSIV_ABI_VERSION`), `game_build`, `rules`, `event_schema`, `record_format`, `save_schema` and `events_save` (the interpreter's save text, `events::kSaveTextVersion`).
* `data`: one entry per kind of JSON object the loaders read, core's first, each sorted by file and object: `file` (`abilities.json` ... `statuses.json`, `game.json`, `journal.json`, `area` for every area file, or `shared` for objects several files hold: `stats`, `variance` and `effects[] <type>`, one per effect type, which abilities, items and equipment uses share), `object` (the path in the file, `[]` for a list's entries, empty for the root), `keys` (exactly the keys the loader accepts there; any other is `unknown field`) and `enums` (key to the name of the word set it takes, for the keys that take one).
* `enums`: each word set by name, values in order: core's from the parsers' own tables (`rules::coreDataEnums`: `ability_kind`, `ai_condition`, `ai_target_rule`, `creature_kind`, `effect_type`, `equip_slot`, `forced_target`, `macro_command`, `macro_target`, `opening`, `stat`, `status_action`, `status_stacking`, `targeting`, `travel_target`) and the game's (`game::gameDataEnums`: `area_kind`, `arrive_notice`, `encounter_mode`, `facing`, `flag_reset`, `flash_level`, `hook_solid`, `hook_trigger`, `interact`, `leave_equipment`, `platform_mode`, `shop_kind`, `step_timing`, `vehicle_opening`, `wander_axis`).
* `script`: `commands` (each command word with its `forms` in `../events/FORMAT.md`'s notation and whether it compiles in a `background` event and runs inside `together`/`race`, `parallel`), `conditions` (the condition forms), `standard_animations` (`name`, `seconds`, `leaves`: `shown`, `hidden` or `as_it_was`) and `action_types` (the presentation action names).
* `text_keys`: the text key families a host or the data provides (`family`, `meaning`).

The report reads the same tables the loaders and the compiler use, so it cannot drift: `rules::DataKeySet` (`core/include/rules/data_keys.h`, sets in `core/src/data_keys.cpp`) and `game::gameDataKeys()` (`src/capabilities.cpp`) are the only things core's `Reader::rejectUnknownKeys` and the game's `JsonReader::only` take (the set's constructor is explicit, so a literal key list does not compile there); the game's word sets are what its parsers look words up in (`gameEnumIndex`); `events::script_commands()` (`events/language.h`) is the parser's list of command words and of where each may stand, and `events::condition_tests()` its condition words. `theLoadersCheckKeysOnlyAgainstTheReportedSets` fails when a loader names a set the report lacks or the report has a set no loader checks; `everyReportedKeyLoadsAndAnUnreportedOneIsRejected` writes every reported key into game.json, its `presentation`, an area, an exit, rules.json and an ability and finds only an unreported key refused; `the_command_table_is_what_the_parser_knows` (events) checks every listed command is one the parser knows. Objects the loaders read as maps by id (`presentation.music.encounters`, `credits`, `vars`, `prices`) have no key set: their keys are ids.

## Data formats

### game.json

`title`, `core_data` (battle data directory, relative to `data/`; `DataDirectories::core` overrides it), `areas`, `events`, `glossary`, `languages` (see [Languages](#languages)), `journal`, `actors` (script actors that are not characters; each needs a `speaker.<id>` string; an entry is an id, or an object with `id` and optionally `sprite` (`{"enemy": id}` of the battle data, or `{"look": name}`), a home with `area` and `at` (a marker of that area or a cell `[x, y]`; both or neither) and `facing`, `solid` (default true: its cell blocks walking while it is shown), and `wander`, `patrol` or `path` (below); see [Actors](#actors)), `presentation` (the `audio`, `cameras`, `layouts`, `animations` and `portraits` the scripts may name, and the optional `music` and `durations`, below), `flags` (every flag a script, hook or journal entry uses; chest flags are declared by their chests; an entry is a name, or `{"id", "reset": "area"}` for a flag that clears whenever the party enters an area, any warp or exit included, the same area too: a door opened by talking that shuts again when the area is entered anew; the save keeps it while the party stays), `vars` (name to starting value), `clear_flag`, `start` (`area`, `marker`, `facing`, `lineup`, `level`, `money`, `items`), `join_levels` (level a character has when an event first adds it), `prices` (buy price per item or equipment id; sell price is the shop's `sell_percent` of it), `item_cap`, `money_cap`, `tick_ms`, `grace_ms`, `round_ms`, `autosave_slots`, `manual_slots`, `bosses` (`encounter` and the `flag` its event sets; pacing keys M5 and M6 by it), `vehicles` (below), `machine_step_heal` (0 to 999: hit points a standing machine member of the party regains with each step, P6), `outside_experience_until` (a flag: until it is set, every member who has joined and is out of the battle gets the share each member standing got, SAV-032; left out, they get none), `leave_equipment` (`keep`, the default, or `bag`: what a member a script removes from the party does with what it wears, P2), `random_encounters_everywhere` (default false: true plays every area in random mode, F1) `grace_after_battle` (default false: every zone's `grace_steps` start again after each battle, as a zone's own `grace_after_battle` does), `interact` (`faced`, the default, or `nearby`; [Interaction](#interaction)), `interact_across` (default false: every point is used across a counter, as a hook's `across` is), `run_speed_percent` (101 to 1000; left out, nothing runs), `background_limit` (1 to 32, default 4: how many background events may run at once; [Background events](#background-events)), `credits` (credits a script's `credits <id>` plays, by id: `music`, an audio id, and `entries`, a list of `{"heading": key}` or `{"line": key}`, text keys of the text tables, each with optional `gap` (0 to 20 empty lines before it, default 0) and `pause_ms` (0 to 60000, how long it holds, default 2000); not part of the content hash; see "Rules this library chose"), `arrive_notice` (`always`, `walked` or `never`; [Interaction](#interaction), "Arrival notices"), `step_timing` (`ticks` or `exact`; [Interaction](#interaction), "Step timing"), `cell_pixels` (1 to 1024, default 16: pixels per cell for actors' `path` offsets and the pixel places the session reports), `machine_step_heal_fallen` (default false: true lets `machine_step_heal` reach fallen machine members too, which so stand up with the notice `game.machine_stood_up`; the research says nothing either way), `party_talk_ambient` (default true; false: entering an area never starts ambient party talk, R114, whatever the profile's `ambient_talk` says; party talk asked for still plays), `vehicle_opening` (`roll`, the default: a battle aboard rolls its opening from the vehicle's agility as a random battle on foot does from the party's; `normal`: it always opens normally and no number is drawn for it; a vehicle's own `opening` wins) and `nameless_actors` (actors of `actors` with no name, such as townsfolk: they need no `speaker.<id>` string and may not have one, and their lines show no speaker, `LineView::speakerName` empty and `lineText()` the text alone). Unknown fields are errors.

```json
"vehicles": [
	{"id": "reed_skimmer", "crosses": ["floor", "water"], "speed_percent": 200, "encounters": [{"encounter": "marsh", "weight": 1}], "call_item": "skimmer_reed"},
	{"id": "rime_borer", "crosses": ["floor"], "breaks": ["barrier"], "breaks_for_good": true, "encounters": [{"encounter": "kites", "weight": 1}], "call_item": "rime_bell"}
]
```

* A vehicle in the field (FLD-060, FLD-061): `id` names one of the battle data's vehicles (core's `party.json`), whose stats, attack and skills fight its vehicle battles; `crosses` the terrain it moves over (`floor`, `water`, `soft`; walls stop every vehicle); `breaks` the terrain it breaks through (`barrier`), turning the cell to floor, for good with `breaks_for_good` (default true) or until the party leaves the area; `call_item` (optional) an item without effects (core's key item) that calls it from the item list (F3); `speed_percent` its speed against walking (10 to 1000, default 100; 200 crosses a cell in half the area's `step_ms`); `encounters` the table its battles draw from (ENC-007). Scripts give and place it (`vehicle give`, `vehicle place`, `../events/FORMAT.md`), and only in `field` areas.

```json
"presentation": {
	"audio": ["battle_brass_warden", "defeat_low_tide", "field_marsh_reeds", "title_harbor_dawn", "victory_bright_sail"],
	"cameras": [
		"wide_shot",
		{"id": "lookout_east", "area": "reed_path", "marker": "lookout_east", "zoom": 1.25},
		{"id": "peddler", "follow": "peddler", "zoom": 1.5},
		{"id": "party", "follow": "leader", "zoom": 0.75}
	],
	"music": {"title": "title_harbor_dawn", "victory": "victory_bright_sail", "defeat": "defeat_low_tide", "encounters": {"warden": "battle_brass_warden"}},
	"durations": [{"action": "panel_show", "seconds": 0.35}, {"action": "panel_show", "subject": "ladder", "seconds": 0.5}]
}
```

* A camera is a name, or an object with an `id` and optionally a target and a `zoom`: `area` and `marker` (a marker of that area), or `follow` (an actor, a character, or `leader` for the party leader); `zoom` (0.25 to 4, default 1) scales the view against the field's own. A host frames panels and the scene with them (`CameraDef`, `PresentationNames::camera`); a camera with no target is the host's to place. The marker must exist, and a followed id must be an actor or a character.
* `music`: tracks outside scripts, each an `audio` id: `title`, `victory` (a won battle's result), `defeat` (a game over), `encounters` (encounter id to track), `vehicles` (a `vehicles` id to the track of random battles fought aboard it; an encounter's own track wins; `Session::battleMusic()`) and `areas` (area id to a track, or to a list whose entries are `{"flag": ..., "track": ...}` or a plain track: the first entry whose flag is set, or that is plain, is the area's track, in place of the area's own; an entry after a plain one is a load problem). The area's track (`Session::areaMusic()`): a script's `music area` until the party leaves the area (`music area default` hands back), else the first matching `areas` entry, else the area's own `music`. Flags are read each time it is asked for, so entering the area and setting a listed flag in it both change it. Scripts' `music play` is unchanged. The loader checks that every vehicle is in `vehicles`, every area exists, every flag is declared and every track is an `audio` id.
* `flash_default` and `flash_original` (R110): the flashing level a new profile starts at in a host (`reduced`, the default when left out, `standard` or `original`; anything else is `data.bad_flash_default`) and whether a host offers `original` at all (default true; false: it does not, and starts a profile whose default is `original` at `reduced`). `GameConfig::presentation.flashDefault` and `flashOriginal`; the session only reports them. Not part of the content hash.
* `animations`: each a name, or an object with `id` and `seconds` (0 to 60), the length of one play; the standard animations (`fade_in` 0.5, `fade_out` 0.5, `dissolve` 0.8, `blink_out` 0.6, `hop` 0.3, `shake` 0.4 seconds) need not be listed, and listing one with seconds changes its length.
* `pictures` (R117): the story pictures scripts' `picture` commands may name (`../events/FORMAT.md`, "Story pictures"); when listed, a name outside the list is a load problem at its script line (the registry's `picture` kind); left out, any name. `Session::pictures()` is the stack up now, bottom first (world chunk `picture` lines, written while any is up). A hide of a picture that is not up warns and changes nothing; game_cli prints each command as an action line (`picture show NAME`, `picture hide NAME`, `picture clear`).
* `music.fade_ms` (R120; 0 to 60000): how long a change of track fades, for area changes and for scripts' `music play` without their own `fade <ms>` or `cut`; left out, -1, the host's own rule. The session puts it in each presented `music play` action's `fade_ms` (the action line then reads `music play TRACK fade MS`); `psiv_game_info.music_fade_ms` gives it for area tracks.
* `durations`: authored seconds per action, as `event_cli time`'s `duration` lines: `action` (`move`, `face`, `anim`, `show`, `hide`, `panel_show`, `panel_hide`, `panel_clear`, `camera_cut`, `camera_move`, `fade_in`, `fade_out`, `shake`, `music_play`, `music_stop`, `music_fade`, `ambient_play`, `ambient_stop`, `sound`, `warp`), an optional `subject` (actor, camera, panel or track) and `seconds` (0 to 60). Each presented action reports its seconds by the timing rule (`events::action_seconds`): the subject's entry, else the action's, else the script's own seconds.
* Nothing in `presentation`, nor an area's `music`, nor a description, is part of the content hash, so editing them leaves saves and records as they were.

### journal.json

```json
{
	"objectives": [{"id": "reach_cove", "text": "objective.reach_cove", "after": "tidewater.met_guide", "until": "cove.warden_beaten"}],
	"jobs": [{"id": "lost_cache", "title": "job.lost_cache", "available": "tidewater.arrived", "accepted": "job.lost_cache.accepted", "completed": "job.lost_cache.done"}],
	"encyclopedia": [{"id": "bell_warden", "title": "codex.bell_warden.title", "text": "codex.bell_warden.text", "flag": "cove.warden_seen"}],
	"party_talk": [{"id": "reeds", "area": "reed_path", "after": "tidewater.met_guide", "lines": [{"speaker": "mystic", "text": "talk.reeds.1"}]}]
}
```

* Texts are string IDs of the dialogue tables, so writers translate them with the scripts and the glossary check covers them. A flag range holds while `after` is set (or left out) and `until` is not set (or left out).
* Objectives (UI-012): the last listed one whose range holds is the quest log's line.
* Jobs: available once `available` is set (or from the start), accepted when `accepted` is set, completed when `completed` is set, and missed for good when the optional `missed` flag is set while the job was never accepted. Scripts set the flags; the state never moves back. Batches are jobs with later `available` flags; a board script that offers a new job only when none is open makes them one at a time (Ember Steps' `steps_board`).
* Encyclopedia entries (TXT-041) unlock when their flag is first set and stay unlocked.
* Party talk sets (FLD-072): a set with an `area` is for that area, one without is a chapter set. Among the sets whose area and range hold, an area set beats a chapter set, then the set with more range bounds wins, then the first listed. Speakers are characters.

### Languages

```json
"languages": [
	{"code": "en", "strings": "text/en.strings", "text": "text/en.json"},
	{"code": "ja", "strings": "text/ja.strings", "text": "text/ja.json"}
]
```

* Each language has a dialogue string table (events format; its `language` line must match `code`) and a text table in core's `{"text": {...}}` format. Core's `text_en.json` is merged into every language's text table, since core ships English only; a game key that core also has is an error.
* The first language is the source: every other text table must have exactly its keys, and the string check (errors for missing script and game IDs, warnings, which fail the strict check, for anything else one table lacks) runs over every dialogue table.
* The profile's `text_language` picks the tables. `setProfile` refuses a language that is not listed; an unknown language in a profile file falls back to the first.
* Text keys the game itself uses: `area.<id>` for each area's display name, `game.*` for notices, `game.refuse.*` for refusals.
* Names (TXT-030, TXT-031): optional text keys `name.<kind>.<id>`, with kind `character`, `ability`, `item`, `equipment`, `status`, `enemy`, `vehicle` or `difficulty`, give a thing's name in that language; without one the battle data's name shows. `Session::displayName` and `difficulties()` read them, so lines, notices, menus and the battle (through the C API's combatant labels) show them. Like descriptions they are left out of the key-for-key rule and the content hash, and a key that names nothing the battle data has is a load problem (`data.name_unknown`). The placeholder's Japanese table names everything; English uses the data's names.
* Descriptions (UI-007) are optional text keys `desc.<kind>.<id>`, with kind `item`, `equipment`, `ability`, `status`, `enemy` or `difficulty` and an id the battle data has: `"desc.item.tonic": "A bitter herbal draught. Restores 30 HP to one ally."`. A missing one shows as empty, in any language, and the key-for-key rule between languages leaves them out; a description key of another kind or id is a load problem (`data.description_unknown`). They are kept out of the content hash, so writing or editing one changes no save or record. `Session::description` reads one; `python3 -I tools/text/cli.py descriptions` counts them per language and kind. String IDs the game shows itself, outside scripts: `choice.yes` and `choice.no` (the answers of every yes/no question), `speaker.<actor>` and every journal text. `GameData::gameStrings` lists them; the loader passes it to the string check so they are not reported unused, and `game_cli --used` prints it for `event_cli --used`.

### Areas

```json
{
	"id": "reed_path", "kind": "field", "encounter_mode": "visible", "step_ms": 250, "music": "field_marsh_reeds", "region": "coast",
	"map": ["#####", "#...#", "....."],
	"markers": {"west_gate": [1, 2]},
	"exits": [{"at": [0, 2], "to": "tidewater", "marker": "east_gate"}],
	"hooks": [{"id": "scout", "at": [3, 1], "trigger": "step", "event": "reed_path_scout", "block_flag": "reed.scout_joined"}],
	"shops": [{"id": "stall", "at": [3, 1], "stock": ["tonic"], "sell_percent": 50}],
	"rests": [{"id": "inn", "at": [3, 1], "cost": 10}],
	"chests": [{"id": "cache", "at": [3, 1], "flag": "chest.cache", "items": {"tonic": 1}, "equipment": {}, "money": 30}],
	"ports": [{"id": "pier", "at": [2, 0], "marker": "west_gate", "flag": "travel.isles_open"}],
	"changes": [{"flag": "reed.bridge_mended", "tile": ".", "cells": [[2, 2]]}],
	"zones": [{"id": "reeds", "from": [1, 1], "to": [3, 2], "table": [{"encounter": "training", "weight": 1}],
		"visible": {"spawns": [[2, 1]], "cap": 2, "detection_radius": 3, "leash_radius": 2, "chase_speed_percent": 110, "chase_ms": 6000, "wander_speed_percent": 50, "wander_percent": 50},
		"random": {"min_steps": 6, "max_steps": 12, "step_distance": 1}}]
}
```

* The display name is the text key `area.<id>`, in every language.
* `music` (optional): the area's track outside events and battles, an id from `game.json`'s `presentation.audio`; `game.json`'s `presentation.music.areas` may give another by flag, and a script's `music area` wins over both.
* `step_ms` (optional, default 250, 50 to 5000): the time to walk one cell; it may have a fraction (`133.5`), kept to the microsecond, which `game.json`'s `step_timing` `exact` keeps on average (below); conveyors' `step_ms` alike.
* `arrive_notice` (optional, default true): false shows no `game.arrive` notice on entering this area and tells hosts not to announce it (`Session::arrivalAnnounced`), whatever `game.json`'s `arrive_notice` says.
* `name` (optional): the text key the area shows as, by where the party came from and by flag: `[{"from": AREA, "flag": FLAG, "key": TEXT_KEY}, ..., {"key": TEXT_KEY}]`, the first entry whose `from` (the area the party was in before this one) and `flag` both hold, the last having neither (`data.area_name_needs_default`, `data.area_name_after_default`); every key in the text tables. `Session::areaNameKey(id)` gives the key, and `displayName(id)`, the arrival notice and `psiv_field_info.area_name`/`area_name_key` use it; `from` applies only to the area the party is in. The area the party came from is saved (world chunk `came_from`) while the area has variants. Left out, `area.<id>`.
* `field_status` (optional, default false): `rules.json`'s `field_poison_every` and `field_paralysis` apply to each step taken here (core's README, rules.json): steps are counted from entering the area (`World::fieldSteps`, world chunk `field_steps`); every Nth a poisoned member of the lineup loses 1 hit point and falls at 0 (`game.poison_fell`; the whole lineup fallen is a game over), and from step `from` a paralyzed member shakes it off on a 1 in `chance` roll from the encounter stream, surely at step `by` (`game.paralysis_worn_off`).
* `platforms` (optional): `[{"id", "from": [x, y], "to": [x, y], "step_ms", "pause_ms", "mode", "require_flag", "block_flag"}]`, moving platforms (`Platform`). `from` and `to` are two cells of one row or column (`data.platform_not_straight`), neither floor nor wall (`data.platform_dock_not_open`: a dock is walked on only with the platform there); `step_ms` (16 to 10000, default the area's) per cell, `pause_ms` (0 to 600000, default 1000) at each end; `mode` `loop` (default: back and forth for good), `one_way` (to `to` once its flags hold, and back to `from` while they do not; entering the area while they hold finds it at `to`) or `triggered` (leaves an end only when the party boarded it there); the flags hold every mode at the end it stands at. Docked at an end, the leader on foot may step onto it (`canStep`, path walking crosses none); the party then rides it: the leader's cell follows the platform (the nearest cell along its run), held input waits until it docks, no step hook or battle roll comes on the way, and the leader steps off at a dock onto a cell it can walk. Followers ride too (a host draws them on it). Entering the area puts every platform at `from` (at `to` for a one-way one whose flags hold) resting its pause; the world chunk keeps each one's place (`platform ID POSITION_US HEADING PAUSE_MS BOARDED`) and the one ridden (`riding_platform`), so a save mid-ride comes back aboard. The data check joins the two docks (one way only for `one_way`), so a region reached only by a platform counts as reached. `Session::platformsHere()` (`PlatformView`: cell, pixel place at `cell_pixels`, end, rest, carrying, run) and `ridingPlatform()`.
* `counters` (optional): `[[x, y], ...]`, cells that are counters (R109) besides the map's `=` cells: never walked, and interaction passes over them (see [Interaction](#interaction)). A listed cell must be in the map and not floor (`data.counter_not_solid`).
* `region` (optional): the world or region the area belongs to (FLD-050, FLD-002). A return to a town reaches the visited towns of the party's region only; areas that leave it out are one region.
* `arrival` (towns only, optional): the marker where a return to the town lands; a town without one is no destination.
* `dungeon_exit` (dungeons only, optional): where leaving the dungeon at once goes from this area, `{"area", "marker"` or `"at", "facing"}`: an area that is not a dungeon, a marker of it or a floor cell `[x, y]` nothing solid stands on (one of the two), and optionally the facing the party arrives with (left out, it keeps its own). Without it, the way out is the cell the party stood on before going in (see "Rules this library chose").
* `ports`: a port of the transport between regions (FLD-051). Like an interact hook it stands on any cell and is used from the floor beside it, which the data check makes sure the party can reach; `marker` is where travellers arrive, in the same area; with `flag`, the port is a place to leave from and arrive at only once the flag is set. Interacting with an open port lists the other open ports without a ship; port ids are unique across areas. With `ship` (a vessel area) the party walks aboard that vessel instead, and its helm lists the other open ports of the same ship (F2).
* `shops`: `kind` (`general`, the default, `weapon`, `armor`, `tool` or `gift`; the label is the front end's, F7), `stock` entries (an id, or `{"id", "require_flag", "block_flag"}` for stock that comes and goes with the story), and `require_flag` and `block_flag` on the shop itself: a shop whose flags do not hold is closed (`game.refuse.shop_closed`), so shops open later or close while a town is emptied (F10). `Session::stock(shop)` and `shopOpen(shop)` read them. Shops and rest points take an optional `voice` (R113): a text key prefix for the keeper's lines, which a host shows as `VOICE.welcome`, `.confirm`, `.thanks` and `.cannot_afford` where the tables have them and as its own default lines otherwise (the defaults are `ui.shop.*` and `ui.inn.*`); `.confirm` is the question asked once the player has picked the item and the quantity, before `buy(id, count)` or `sell(id, count)` (one call for any quantity: one total price, money and carry check, R124), or before a rest (an inn's `ui.inn.confirm` takes `{0}`, the price from `restCost`); the data check wants at least one of the four in the first language's table (`data.voice_unused`).
* `rests`: `cost` (0 to 1000000), `keeper`, `voice` (above) and `per_member` (R113, default false): the price is `cost` times the lineup's size when the party rests, in the inn's offer (`game.inn_offer`) and the money check (`game.refuse.no_money`); `Session::restCost(point)` gives it.
* Areas can be drawn in Tiled: `data/maps/NAME.tmj` is the source of `data/areas/NAME.json`, regenerated with `make maps` (mapping: [`tools/maps/README.md`](../tools/maps/README.md)). `make test` fails when a generated file is stale. Edit the `.tmj`, not the generated file.
* Map rows: `.` floor, `#` wall (blocks sight), `~` water, `:` soft ground, `=` a counter (R109: never walked, no vehicle crosses it, interaction passes over it) and `%` a barrier wall (both crossed only by a vehicle whose `crosses` or `breaks` names them, F3). Cells are `[x, y]` from the top left. Only floor is walked on foot. Soft ground is the sand, bog and quicksand the published vehicle notes give one land vehicle (published-mechanics.md, FLD-062), so sand needs no terrain of its own: write it `:`.
* `exits` may carry `sound` (R119): a cue of `presentation.audio` (else `data.exit_sound_not_audio` at the exit's line) a host plays as the party leaves by that exit; `Session::exitSound()` (C `psiv_field_info.exit_sound`, also on `psiv_exit.sound`) names it for the entry that followed, empty after any other way in, and game_cli prints `exit sound CUE`.
* A door: an `interact` hook may stand on the cell of an exit that has `require_flag` or `block_flag`. While the exit is closed the hook answers from beside it (`interactTarget()`, `interactAt()`), the cell blocking as any interact hook does; once the exit opens the hook is passed by and stepping on the cell uses the exit. The data check accepts the hook there only on a gated exit (`check.exit_on_object` otherwise) and counts the exit as reached through it.
* `exits` may carry `require_flag` and `block_flag`: while they do not hold, the exit is closed and its cell is a wall in `Session::area()` (and in the C API's rows), so nothing walks onto it. With `closed_tile` (`wall`, the default, `normal` for the tile the map has there, or one map character) a closed exit is drawn as that instead and still blocks walking, on foot and aboard (`Area::closed`): a door drawn as floor, which a host draws its door over (the C API's exits say `open` and `closed_tile`). Map `changes` cannot do this, since a cell's tile also decides whether it is walked: a door made with changes (a wall cell that a flag turns to floor, with the exit on the floor beside it) is drawn as wall while shut. `ports` may carry `block_flag`, which closes an open port again (`portOpen`).
* Hooks: a `flag` hook with `once: true` fires once per game without a block flag (the save keeps `<area>/<hook>`); a `step` hook may give `tile` (one map character other than `#`) in place of `at`, firing on entering any cell of that character (`Area::stepHookAt`); an `interact` hook with `solid: "while_active"` (default `always`) blocks the way only while its flags hold and, for an actor's talk point, while the actor is shown, and its actor is not shown at home while its flags do not hold; an `interact` hook may give `across: true` (used from the cell beyond a counter straight ahead) and `cells` (`[[x, y], ...]`, further cells it covers, each solid and answering as the hook; not its own cell or its actor's); an `interact` hook may give `actor_at` (a cell `[x, y]` of the area, not the hook's own), where its actor stands, is drawn and is scripted while the party talks to the hook's cell (only an interact hook whose id is a `game.json` actor; `data.actor_at_interact_hooks_only`, `data.actor_at_not_actor`, `data.actor_at_on_hook`). That cell blocks walking while the actor is shown there, and the data check treats it as solid but not as a point: it blocks the reach of everything else, yet needs no floor beside it (see [Checking data](#checking-data)).
* `conveyors` (optional): `[{"cells": [[x, y], ...], "direction": "north|east|south|west", "step_ms": 250, "require_flag", "block_flag"}]`. Two belts may cover the same cells with opposite flags: only the one whose flags hold carries the party (test `oppositeBeltsOnOneCellAndFractionalBeltSteps`), and a fractional `step_ms` is kept to the microsecond under `step_timing` `exact` and rounded for the millisecond fields. While the leader stands on a cell of a conveyor whose flags hold, with player control, the conveyor carries it one cell in its direction every `step_ms` (16 to 10000), through `arrive` like a step (exits, step hooks and battle rolls apply), and held input is ignored; a cell it cannot enter stops it. Path walking (`walkStep`) crosses no conveyor cell but its goal. An elevator is a step hook whose event warps.
* `changes` (F8, F10): cells that become `tile` while `flag` is set (a bridge repaired, a barrier or an illusion gone, a place sealed for good, a gate a switch opens). Later changes win on a cell they share. `Session::area()` applies them, and the broken barriers, to the rows; markers and exits must stand on floor in the map as written. The data check counts a cell a change turns to floor as floor.
* An exit with `"fall": true` is a pit (F8): stepping on it drops the party to its marker, announced as a fall (`game.fell`). An exit to a marker of the same area is a transport tile.
* `kind: vessel` is a ship's inside (F2): no battles, no vehicles, no returns to a town (`game.refuse.on_ship`). Its `arrival` marker is where the party walks aboard, its `helms` (`[{"id", "at"}]`, solid, on any cell like a port) open the ship's destination menu, and stepping on a `gangway` cell takes the party back ashore at the port it boarded from.
* `kind`: `town` (no random battles), `field` or `dungeon` (M6 runs from entry to the boss's end). Vehicles move only in `field` areas, and a return to a town does not work in a `dungeon`, where the way out does.
* `encounter_mode` (ENC-002): `visible` or `random`; `SessionOptions::encounterMode` overrides it for every area, which is how the bot compares the two.
* Hook `trigger`: `interact` (the cell the leader faces; the cell is solid), `step` (entering the cell), `load` (area entry, once per entry), `flag` (whenever control is in the field and the flags hold; needs `block_flag`) or `touch` (with `actor`, an actor of `game.json`, and no `at`: the leader walking into that actor, the actor wandering into the leader, or interact with it). `require_flag` and `block_flag` gate every hook. A hook whose event is marked `background` runs it beside the field (see [Background events](#background-events)).
* Shops and rest points may name their `keeper`, an actor of `game.json` (`Shop::keeper`, `RestPoint::keeper`; `data.keeper_not_actor`).
* Shops, rest points, chests and interact hooks stand on solid cells, interacted with from the next cell while facing them. Shops, rest points, chests and step hooks stand on floor; an interact hook may stand on any cell of the map, so a sign on a wall or a ladder up a cliff is used from the floor beside it (FLD-030). The data check reports one with no floor beside it that the party can reach. A chest's flag is set when opened and never cleared, and the area's flag hooks run as part of opening it.
* Visible zone values are the ENC-012/013 defaults when left out. Random thresholds are drawn uniformly between `min_steps` and `max_steps` (the original's distribution is ENC-005). Optional in `random`: `grace_steps` (0 to 1000: no roll for that many steps after entering the area, so the first roll is on the next step; the save keeps the count), `step_chance` (1 to 10000: each step starts a battle with a 1 in N chance from the encounter stream, in place of the counter), `vehicle_step_chance` (the N aboard a vehicle; without it aboard uses `step_chance`), `safe_near_exits` (no roll while the leader stands on or next to an exit), and `grace_after_battle` (needs `grace_steps`: the grace starts again after every battle that ends with the party in this zone, won, escaped or scripted, on foot and aboard; `game.json` `grace_after_battle` does the same for every zone). `step_chance` has no step count at which a battle must come: each step rolls on its own. The counter has one, `max_steps`; `max_steps: 0` (R115) takes it away: it needs a `step_chance` (`data.max_steps_zero_needs_chance`), and no step rolls until `min_steps` steps (times `step_distance`) are counted since the last battle, after which each step rolls the chance with no cap. A tool-assisted run's ten safe steps after each area change and blocked battles near towns (published-mechanics.md, ENC-005, medium) fit `grace_steps` and `safe_near_exits`; the original's step distribution stays to measure, so the counter remains the default.

### Event scripts and text

The `events/` format (`../events/FORMAT.md`). The loader builds an `events::Registry` from the data (actors, characters, the markers of each area with their area, the area each hook's event starts in, presentation names, items and equipment, encounters, enemies, vehicles, areas, shops, rest points, flags and variables) and compiles against it, so an unknown name, an undeclared flag, a warp to a marker in another area, or a move to a marker outside the area the party is in is a load error. It then applies the strict check: compiler warnings are errors, every player-facing text is a string ID in every language's table, the tables match the scripts and each other, and glossary names are written as name tokens. A `battle ... until defeat <enemy>` must name an enemy of that encounter. A `battle <encounter> aboard <vehicle>` is a vehicle battle (core's `flags.vehicleBattle`): the vehicle fights and the active party rides aboard. `vehicle give` and `vehicle place` must name a vehicle with field rules in `game.json` (`data.vehicle_not_field`) and a marker of a `field` area (`data.vehicle_not_outdoors`). Load problems from every part of the data (core's battle data, the scripts and the game's own files) are in `Result::problems` with a text key and parameters; `problemText()` has the English template of every key, and `error` lists the same problems as English lines. `game_cli --registry` and `game_cli --used` print the registry and the game's own string IDs, so `event_cli check --strict --registry --used` can run on the same scripts; `make test` does.

Shop and rest point ids are unique across areas, so a script names them without an area. A shop or rest point without `at` is reached only from a script.

### Saves

A text file, platform independent:

```
PSR-SAVE 10
chunk header 1 <payload bytes>
schema 10
...
chunk location 1 <n>
...
end <FNV-1a 64 of everything before this line, 16 hex digits>
```

Chunks and versions (a chunk is read from the oldest version listed up to the current, since the newer ones only add lines): `header` 1 (schema, build, rules version, content hash, write time, sequence, autosave, play time, area, party, difficulty, and `dev 1` for a game developer tools marked: enough for the slot list), `location` 1, `party` 5 (members with statuses that persist outside battle, chosen names, from version 3 `taught` lines: abilities learned for good, from version 4 a piece worn in the `left_hand`, and from version 5 `snapshot` lines: a party snapshot's name, how many of the ids after it are its lineup, then the lineup and the reserve; read from 2), `inventory` 1, `world` 3 (flags, variables, visited areas, control lock, visible enemies of the current area, grace, random counter, play time, from version 2 the `follower`, and from version 3 `area_steps` (steps in the area, kept only up to its zones' longest grace), `once` lines (once hooks fired, `<area>/<hook>`) and `area_music` (a script's track for the area); read from 1), `battle` 3 (the auto macro, then core's `serializeMacros` and `serializeComboLog` blocks; from version 3 the macros block is version 2, whose steps may name a piece; read from 2), `random` 1 (the encounter stream's `rules::Rng` state), `difficulty` 1, `quests` 1 (job states), `unlocks` 1 (encyclopedia entries), `actors` 2 (one `actor` line per actor a script touched: id, area or `-`, x, y, facing, visible; from version 2, after it, `vanish` (id and `faded`, `dissolved` or `blinked_out`), `anim` (id, animation, milliseconds left and in all) and `removed` (id and `until_reload` or `for_good`), `look` (id, enemy or `-`, look or `-`) and `wander` (id, progress in hundredths of a cell, pause milliseconds) lines when they apply; read from 1), `talk` 1 (one `heard` line per party talk set that came up by itself in an area, as `<set>@<area>`), `travel` 3 (`aboard` and the vehicle the party rides or `-`; one `vehicle` line per vehicle the party has: id, area, x, y, facing, then the area and cell of its last boarding point, each followed from version 2 by `uses` lines, its skill uses left; read from 1; `dungeon_exit` and the area and cell the way out of the dungeon leads to, `-` when there is none; from version 3 `ship` and the port the party walked aboard from while it is in a vessel, `broken` lines (area, x, y) for barriers broken for good and `broken_here` lines for those broken in the current area until it leaves), `dev` 1 (`marked 1` when developer tools marked the game, empty otherwise; [`docs/dev-tools.md`](../docs/dev-tools.md), "The dev mark"), `midevent` 1 (in the autosave before an event battle, and in `Session::saveText` while an event runs: `events::save_state_to_text`, `events-save 3`) and `background` 1 (while background events run: one `event` line each, its name and its `events::save_state_to_text`). Every known chunk but `midevent` and `background` must be present. Values are tokens with letters, digits, `_` and `.` kept and every other byte as `%XX`; empty is `-`. Unknown chunks are kept in `World::unknownChunks` and written back unchanged after the known ones. A known chunk with a higher version, or a higher schema, is refused as "from a newer build". A checksum mismatch is refused as damaged and listed as damaged. Writes go to `slot.sav.tmp` and are renamed over the slot.

Migrations (SAV-021) run in order on the chunk list before it is read. Schema 1 to 2: the battle chunk's own macro and combo lines become core's blocks (combinations found before get play time 0 and no participants), the party chunk moves to version 2 unchanged, empty `quests` and `unlocks` chunks are added and filled from the flags on load, and a `midevent` chunk is dropped, because its `events-save 2` text no longer loads; such a save continues in the field. Schema 2 to 3: an empty `actors` chunk is added, so every actor stands at its talk point; a `midevent` chunk stays, and the resumed event rebuilds the actors it had moved. Schema 3 to 4: an empty `talk` chunk is added, so party talk can come up by itself once more in each area. Schema 4 to 5: an empty `travel` chunk is added: no vehicle, on foot, no way out of a dungeon known. Schema 5 to 6: an empty `dev` chunk is added: the game is not marked. Schema 6 to 7 changes nothing: its party, world and travel chunks simply lack the new lines (nothing taught, no follower, every vehicle skill full). Schema 7 to 8 changes nothing either: nobody wears a piece in the left hand, the party is ashore and no barrier is broken. Schema 8 to 9 changes nothing: no steps counted, no once hook fired, no script music. Schema 9 to 10 changes nothing either: its battle chunk 2 holds a macros block 1, which reads as it is. Schema 10 to 11 changes nothing: its actors chunk 1 has no `vanish`, `anim` or `removed` lines, so every actor it names is plainly shown or hidden, with nothing playing and nothing removed, and its party chunk 4 has no `snapshot` lines. Schema 11 to 12 changes nothing (no picture up, the camera on the leader). Schema 12 to 13 changes nothing either: the actors chunk's `patrol` and `path` lines, the world chunk's `platform`, `riding_platform` and `field_steps` lines and the party chunk's `affinity` lines (a member's permanent affinities) are written only when they apply, so a schema 12 save starts patrols and paths from their first entry and the area's platforms where entering it puts them.

Loading checks the world against the data before it is used (`game.refuse.save_invalid`, naming the problem): the party's cell inside its area; members, lineup, names, items and pieces (counts 1 to `item_cap`), money (0 to `money_cap`), declared global flags and variables, macros (at most 8, an enemy position 0 to 7, each step's member a character or a vehicle of the data, at most five member steps beside the vehicles' steps, a vehicle's step without an item, piece, defend or member target), combinations, visited areas, visible enemies (zone, encounter, cells inside), actors, vehicles and their skill uses (cells inside their areas), the vehicle ridden, the follower, the way out, the ship's port, broken barriers (known areas, cells inside), jobs, encyclopedia entries, the difficulty, no negative grace, counter or play time; numbers outside a 32-bit integer are damage. A mid-event save's event-start world is checked the same way before it is restored. Hit and technique points above a maximum the data has since lowered are trimmed to it. Tests load a hand-written schema 1 save, one written without the `actors`, `talk`, `travel` and `dev` chunks as schema 2, and the acceptance check also one without the `talk`, `travel` and `dev` chunks as schema 3, one without the `travel` and `dev` chunks as schema 4, and one without the `dev` chunk as schema 5.

Slots are `manual_0` .. `manual_9` and `auto_0` .. `auto_2` in the save directory. An autosave writes an empty or damaged autosave slot, otherwise the one with the lowest sequence number. Continue loads the newest undamaged save by write time.

The same directory holds `profile.cfg`, the global profile (`PSR-PROFILE 1`, one `key value` line per setting, then `end` and the checksum; unknown keys are kept and written back; a damaged file means default settings and a warning), and `clear.sav`, the clear-data record (SAV-024: `PSR-CLEAR 1` with the header, party, inventory and world chunks; `parseClearRecord` reads it).

## Rules this library chose

Where the spec is "To measure" the proposed default is implemented and kept in data; where it is silent the choice is listed here.

* Modes: Title, Field, Event (the spec's Cutscene), Battle, Menu, Shop. Shop follows the Menu rows. A Menu or Shop only closes back to the mode that opened it. Quit to Title (FLOW-022) resets the machine instead of using a transition, since the table has no Field to Title row.
* Grid field: interaction range is the faced cell (FLD-030) by default; contact (ENC-011) is one body trying to step into the other's cell; the rear 90-degree arc is ±45 degrees, inclusive, around the back direction (ENC-020/021).
* Interaction rules ([Interaction](#interaction)): the faced cell always wins, and a cell that holds something whose interact would refuse is still the target there (its refusal stands); other neighbors are tried right of the facing, left of it, then behind, passing by any that would refuse; a counter is any cell that is not floor and holds no point, exit or solid actor, so `interact_across` reaches over walls too (off by default); an actor answers where it stands only under `nearby`, through its talk point's event; a hook's further `cells` are listed one point each by the C API. Running is on foot only, scales the step time alone, and `always_run` turns the run input around (held, the leader walks); it is a profile setting, since it is an input preference, not part of a game.
* Battles aboard (`vehicle_opening`): the research says nothing about the opening of a vehicle battle. `original-battle-rules.md` section 8 lists what differs aboard (one fighter, its own menu, full hit points, halved experience, no macro reordering) and names no opening rule, and the opening roll of ENC-024 (published-mechanics.md) is read for battles in general; so the roll, from the vehicle's agility, stays the default and `normal` is the option.
* Grace (ENC-015): for `grace_ms` after any battle no enemy chases or starts a battle, and the leader cannot walk through one. An escaped group returns to its leash. Defeated groups come back on area re-entry (ENC-014).
* Random mode: the counter freezes in towns, during grace and outside zones (ENC-042); the opening comes from `rules::openingFromRoll`: the fastest living member's agility against the encounter's awareness (ENC-022).
* Battle seeds come from the encounter stream; a retry XORs in a retry counter (BAT-134). Retry (FLOW-042) exists only where an autosave before the lost battle exists, which is event battles.
* Defeat without a defeat branch is a game over (FLOW-041 to measure): back to Title, where Continue loads the newest save. A defeat with a `lose` branch stands fallen members up with 1 hit point before the branch runs.
* Event battles: escape needs both the script's `flee` section and the encounter's escape flag. The opening comes from the script. The scripted end comes from the script (`until survive N`, `until defeat ENEMY`, using the enemy's first formation position); it pays the fallen enemies' rewards and returns to the `win` branch.
* Battle drops (core's `rewards().items`) go to the inventory after experience and money, up to `item_cap`, each with a `game.dropped` notice. The reward multiplier does not scale them (SAV-023).
* Autosaves (FLOW-050): area entry when the area was not visited since the last autosave, event end when the script changed any flag, before every event battle (written from inside `start_battle`, with interpreter state), after rest (inn or script). The pre-battle autosave holds the encounter stream from before the battle seed was drawn, so loading it sets up the same battle; setting that battle up again from its own autosave writes no second one.
* Rest (FLD-034/035): `rules::rest` for the whole roster, active or not, which cures the statuses with `rest_cures`. A script's `rest` with no rest point is free; with one it charges the point's cost, and without the money the party does not rest and the script carries on.
* Statuses that persist outside battle stay on the members between battles, show in `status`, are saved, and are cured by rest or by field items and techniques.
* Experience (SAV-032, read from the disassembly in original-battle-rules.md section 5): members who have joined and are out of the battle get the full share a standing member got until `outside_experience_until` is set, then nothing; the placeholder sets it to `saltgrass.kiln_done`. The roster is exactly the members who have joined, which is the original's per-character flag. A member who leaves stays in the roster wearing its pieces, so they go with it, and comes back at the level that experience gave it (SAV-035 is to measure).
* Machine members (P6): a standing one regains `machine_step_heal` hit points with each step the party takes (placeholder 1; nothing published gives the number); core stands a fallen one up after a won or escaped battle.
* Vehicle skill uses (B19) carry from battle to battle in the save's travel chunk; rest (inn or script) refills them with the party, as nothing published says when the original refills them.
* `learn` adds an ability to a member who has joined (a notice; nothing when it already knows it); `follower` sets the actor who walks with the party, saved; where it is drawn is the front end's business (the sample puts it last in the walking line). A script hides the actor's talk-point figure while it follows (Ember Steps).
* Encounter mode (F1): the spec keeps visible enemies as the design (ENC-001) and random battles as a per-area option (ENC-002), so the placeholder default stays `visible`; the Drowned Kiln's lower floor, Ember Steps, the Fell Moor and the Fell Vault are `random` (no visible enemies). `game.json` `random_encounters_everywhere` turns every area random at once, for a build that drops visible enemies; the placeholder leaves it off. `SessionOptions::encounterMode` still wins over both.
* Leaving members (P2, SAV-034, SAV-035 to measure): `party remove` leaves the member in the roster, so it goes on sharing experience while away (SAV-032) and comes back at the level that gave it, with the abilities those levels teach. What it wears follows `leave_equipment`: `keep` (the placeholder's), which matches the published note that a member who leaves for good takes what it wears, or `bag`, which hands every piece back (`game.equipment_returned`).
* Party snapshots and swaps (R73, R74; `../events/FORMAT.md`, "Game state"): `party save NAME` keeps the lineup and the reserve (roster members not in the lineup, in roster order) in `World::partySnapshots`, replacing an earlier one of that name; snapshots are saved and stay after a restore. `party restore NAME` makes the snapshot's lineup the lineup and reorders the roster as the snapshot's lineup, then its reserve, then everyone who joined since, so a member who joined since stays in the reserve unless the snapshot names it. The roster never loses a member (`party remove` only leaves the lineup), so a member who left since the snapshot comes back to its place. Levels, equipment, hit points and statuses do not change, and the notice is `game.party_restored`. A snapshot that names nobody who has joined warns and changes nothing; an unknown name is the interpreter's runtime error (`event error: FILE:LINE: ...`). `party swap SLOT|MEMBER MEMBER [equipment keep|bag]` puts a member who has joined and is not in the lineup in that lineup slot (1 is the leader) or in the named member's; the lineup does not grow, so its limit holds. The replaced member goes to the reserve (`game.party_swapped`) and hands back what it wears by `leave_equipment`, or keeps it with `equipment keep`, or hands it back with `equipment bag` (`game.equipment_returned`). A swap with an empty slot, a member who has not joined, or one already in the lineup warns and changes nothing, like a refused `equip`. `party order MEMBER...` (R97) moves the named lineup members to the front in that order, the others following in their own order, with no notice; a name not in the lineup is the interpreter's runtime error and the lineup stays. `silent` on `party add`, `party remove` and `party swap` makes the same change without `game.joins`, `game.leaves` or `game.party_swapped` (`game.equipment_returned` still shows when pieces go back to the bag). Party changes stay event-only: the field menu still only reorders the lineup.
* The last place in the party (P4) is story content, not a rule: Ashfall's lodge offers two candidates through a `choice` and swaps them later with `party remove` and `party add`, using the script's `party` test. The one left at the lodge keeps its pieces and its share of experience.
* Core's rule options (`../core/README.md`, rules.json: `affinity_divisor`, `magic_defense`, `instant_defeat_kinds`, and `next_form_at`, `vulnerable`, an instant defeat's `element`) need nothing from the session; the placeholder leaves the switches off. The Gloam Reaper (`reaper`) and the Shellback (`shellback`) are encounters no zone draws, for tests and the sample's developer battles; the Ward Mantle is sold in Ashfall's better armor shop.
* Two hands (P10): the rules are core's (`../core/README.md`, equipment.json). The session's `equip(member, piece)` puts a piece at its default position, `equip(member, piece, position)` in a hand; `equipPreview` takes the position too and names the other hand's piece a two-handed weapon sends back (`alsoReplaces`).
* Ships (F2): a port with a `ship` puts the party aboard the vessel area at its arrival marker, the port kept as `World::shipPort` (saved); the helm opens the port menu for that ship, listing its other open ports, and travel lands at the chosen port's marker. The gangway leads back to the port boarded from. Ferry ports (no ship) and ship ports never list each other. No fare, as for the ferry. A vessel is no place for returns to a town, vehicles or battles. A port whose flag is not set is "not there yet" for a front end (the sample draws none).
* Vehicles by terrain (F3, FLD-062 to measure): soft ground (`:`) is crossed only by a vehicle that lists `soft`; a barrier (`%`) only by one that `breaks` it, which turns the cell to floor as the vehicle enters it (`game.barrier_broken`). Whether a broken barrier stays broken is data (`breaks_for_good`; the placeholder's borer breaks for good, since nothing published says the walls grow back); a barrier broken otherwise is whole again once the party leaves the area. Calling (published: vehicles are boarded from the Item menu outdoors): using a vehicle's `call_item` from the field menu, in a `field` area on a cell the vehicle can stand on, brings the party's vehicle there from wherever it was and boards it (`game.vehicle_called`), closing the menu; it is refused elsewhere (`game.refuse.call_outdoors`), aboard, or when the party does not have the vehicle (`game.refuse.vehicle_not_owned`). The item is not used up.
* Shops (F7, F10): a shop's kind is a label; stock and doors follow flags. Closing while a town is emptied is the same `block_flag` that hides the townsfolk's hooks; scripts `hide` and `show` the actors.
* Dungeon mechanisms (F8, FLD-043 and FLD-044 to measure): data for cells that change by flag, pits (exits with `fall`), transport tiles (exits within the area), and scripts for the rest: a switch toggles a flag, a locked door opens for a party holding its key (the script's `item` test), an illusion is a wall cell a scene removes, a barrier is removed by the story's flag. The vault's layout gives the locked door another way round, through the pit and the stairs.
* Inventory caps (SAV-036): `item_cap` per id, `money_cap`. Worn pieces cannot be sold.
* Field items and techniques go through core's `useItemOutsideBattle` and `useAbilityOutsideBattle`, on the active party. An item that changes nothing is not used up.
* Manual saves (SAV-003/004): from the field menu, anywhere, never during an event. A script's `save prompt` writes an ordinary save without interpreter state and with player control on, so loading it returns to a playable field.
* Name entry: 1 to 16 characters, no control characters, spaces at the ends dropped. Any character can be named, joined or not. The name replaces the character's name in lines, speakers, notices and battle combatants (core's `PartyMember::name` on the battle's copy of the party; the name itself stays in `World::memberNames`).
* Play time (SAV-037) counts field, event and menu time, plus `round_ms` per battle round, because headless battles have no clock. Pacing battle time (M3) uses the same number.
* Pacing: M1 is battles per area visit (no exit landmarks yet), M2 the median field time and steps between battles, M5 the active party's average level when a boss battle is set up, M6 dungeon entry to boss victory.
* Settings: difficulty, reward multiplier and the auto-battle macro are per save; everything else in UI-013 is the profile. UI-013 lists the auto-battle macro as a setting, but it names one of the save's macros and SAV-001 puts it in the save.
* Quests and unlocks: job states and encyclopedia unlocks are saved, because they never move back even if their flags are cleared. The objective line is not saved; it follows the flags.
* Party talk: lines of characters not in the active party are left out; a set with no line left says nothing. Party talk is not added to the text log.
* Text log (TXT-027 to TXT-029): event lines shown and lines a skip passed over (marked), the last 500 since the game was loaded or started, rendered with the current names setting, not saved.
* The clear-data record is written when control returns after `clear_flag` is first set, and replaces any earlier one. A script's `end game` writes it too, when the event ends (a game a developer command marked writes none and says so, `game.clear_not_recorded`, as with the flag), then goes back to the title (R102).
* Credits (R102): a script's `credits <id>` opens the `game.json` credits of that id as a menu (`MenuKind::Credits`) the event waits on, and stops a skip. Entry `i` counts as shown once the play time since they began reaches the pauses of the entries before it; the session never closes them itself, so a front end can let the player wait on the last entry or leave early, and `closeMenu()` is its "finished". Saving is refused while they play (`game.refuse.save_where`, as anywhere but the field menu and a save prompt), the field menu does not open, and no autosave falls inside an event, so nothing has to save or restore a game in the middle of its credits.
* Speaker names are string IDs (`speaker.<id>`) in the dialogue tables, or the character's chosen or data name. Character data names come from core's data, which has one language.
* A yes/no question's answers are the dialogue table strings `choice.yes` and `choice.no`, in every language, so the loader requires them in every table.
* The ended battle stays readable until the next battle starts, `dismissBattle()`, a new game, a load (Continue and Retry included) or `quitToTitle()`: those replace the world it was fought in. Its rewards are what was paid out, so they are empty after a defeat or an escape.
* Field input: the last direction pressed since the previous tick plays as held for one tick, which turns the leader and starts no step on its own (a step needs `step_ms` of held input). Leaving the field clears it. Ticks stay fixed, so a run is still determined by the updates it gets.
* `face()` is refused outside the field and while a script holds player control, like walking.
* Path walking (`walkStep`) uses walkable cells only, never steps on an exit other than the goal, and ignores visible enemies, so bumping into one starts its battle; after a refused step (an enemy in the way during grace) it lets one tick pass. It gives up after 4000 steps. `playBattle` stops after 60 rounds by default.
* Presentation: Instant keeps the last 256 actions for `pollActions()`, so a host that never polls does not grow the queue without bound; Queued keeps them all, since the host must finish each.
* Vehicles in the field and travel follow the spec where it speaks (FLD-030 vehicles are interactables, FLD-061 terrain, speed and boarding rules kept in data, FLD-063 a vehicle left out of reach returns to its last boarding point and positions are saved, ENC-007 battles aboard are vehicle battles from the vehicle's own table, FLOW-050 an autosave after a vehicle is acquired, FLD-051/052 the fast travel the original has, as `docs/research/published-mechanics.md` describes it: a return to a visited town of the planet outside dungeons and battle, a way out of the dungeon to its entrance outside battle, a transport between worlds from a destination menu at ports that the story unlocks). The rest are choices made here, not asked for by the spec, and the real rules (FLD-052, FLD-062) replace them as data where they differ:
  * Terrain is the map's own: a vehicle crosses `floor`, `water` or both; walls stop it, and so do interactables and the party's other vehicles. A vehicle moves only in `field` areas: `vehicle give` and `vehicle place` are refused elsewhere at load. On foot, a parked vehicle is solid, like an interactable.
  * Boarding: `interact()` (or `board()`) facing the vehicle; the party takes the vehicle's cell, and that cell becomes its last boarding point. Aboard, `interact()` is refused (`game.refuse.aboard`), so nobody talks or opens chests from the hull. Leaving: onto the faced cell, else the first of north, east, south and west that the party could walk on (floor, no interactable, no exit, no enemy, no other vehicle); refused when none (`game.refuse.nowhere_leave`). Leaving puts nothing on the step-hook or encounter path: the party simply stands there.
  * Speed: `speed_percent` scales the area's `step_ms` (the published "two tiles per step" fits 200). Visible enemies keep their groups but neither notice nor chase the party aboard, and block the vehicle like walls (`tickVisibleEnemies`'s `leaderUnseen`). Battles aboard come from the random counter of the zone the vehicle is in, in both encounter modes, with the zone's thresholds and the vehicle's `encounters` table; the opening rolls the vehicle's agility, since it alone fights. After the battle the party is still aboard.
  * Exits: an exit into another `field` area takes the vehicle along when it can stand on the arrival marker; an exit into a town or a dungeon (or onto a marker it cannot cross) leaves it on the last cell before the exit (`game.vehicle_parked`), as the published rule "entering a town parks the vehicle" describes.
  * FLD-063: a vehicle left where the party cannot reach it (neither on floor nor beside a cell the party can walk on), by a script's warp, a travel, or an exit, goes back to its last boarding point (`game.vehicle_returned`). `vehicle place` and `vehicle give` set that point too. `vehicle remove`, and `vehicle place` of the ridden vehicle, set the party down on its cell or the nearest cell it can walk on.
  * Regions are an area field, not a separate world map layer: FLD-050 makes each planet a set of connected zones, which areas and exits already are.
  * The transport is ports in area data (the original's spaceports): open ports, by their flag, list each other; travel takes no money, since nothing published gives a fare. It goes to the destination port's marker.
  * Returns: from the field menu with an item or technique whose core effect is `travel` to `town`; the destinations are the visited towns of the party's region that have an `arrival` marker, the area the party is in left out; refused in a dungeon. The way out: `travel` to `dungeon_exit`, only in a dungeon, to the `dungeon_exit` of the dungeon area the party is in when the data names one (each floor of a dungeon may name its own, and a dungeon reached by a script warp with no way in recorded still has it; the area's, not the first dungeon's, since each floor's data is where an importer finds the original's exit, R101), else back to the cell the party stood on in the last non-dungeon area before it entered a dungeon (kept in the save; a dungeon entered from another dungeon keeps the first one's way out; one entered by a script warp from outside records the cell the party stood on). A vehicle the party rides when it travels stays behind as above. The item or technique is spent through core's field use, so technique points, silences and stock are core's checks.
  * The vehicle's acquisition autosave (FLOW-050) is `vehicle give` of a vehicle the party did not have, written when control returns, like the event-end one, whose reason it replaces.
* Party order: `swapLineup` swaps two lineup positions, the leader's included, from the field menu only. It never changes who is in the lineup, so SAV-034 (the party changes only through events) holds and there is no swap with members outside it. Saves keep the order (the party chunk's `lineup` line).
* Macro editor (UI-005): changes only from the field menu, like equipment; reads any time. At most 8 macros, the original's count (BAT-055, BAT-057), and one step per party member, so at most 5 steps (BAT-050). A new macro goes at the end. Names follow the name entry rule (1 to 16 bytes, no control characters, spaces at the ends dropped) and are unique. A step names a member of the roster or a vehicle of the battle data (R95): a vehicle's step is used only in battles aboard that vehicle, where members aboard pass their steps by, and is passed by in party battles; it attacks, uses one of the vehicle's skills or escapes (an item, piece or defend step is `game.refuse.macro_bad_command`, a member target `game.refuse.macro_target`), and vehicle steps do not count toward the five member steps, one per vehicle. Its mark is `not_in_party` while the party has no such vehicle, `unknown_ability` for a skill the vehicle lacks and `no_uses_left` when the vehicle's kept uses of that skill are spent. `fight NAME`, the save's auto macro and an auto play macro use such steps in battles aboard. Saves keep such steps as core writes them and load them again. An ability step needs an ability the member knows now (data macros may name one learned later, as core's loader allows); an item step needs an item that exists, held or not; the target rule must fit the command, by core's own check (`rules::macroTargetFits`), and an enemy position is 0 to 7. Target fields the rule does not use are cleared. Deleting the auto macro turns auto-battle's macro off and says so with the notice `game.auto_macro_cleared`; renaming it keeps it as the auto macro. A piece step (`MacroStep::piece`) names an equipment piece with a battle use (`game.refuse.macro_piece_no_use` otherwise), held or not. A step's mark (`MacroStepView::issue`) is judged on the member outside battle: not in the lineup, defeated, the ability not known, techniques blocked by a status, not enough technique points, no skill uses left, the item not held, or for a piece step neither worn by the member nor in the bag with `use_from_bag`.
* The terminal's `autobattle random` plays alone every battle the field starts, visible-enemy contacts and developer battles included, not only the random counter's: the battles it leaves to the script are those an event starts.
* Member detail: experience to the next level is core's curve less the experience carried in the current level, 0 at the level cap; the stats, the weapon's element, the affinities and the status resistances come from core's `memberCombatant`, the combatant a battle sets up.
* Equipment comparison (UI-008, UI-009): `equipPreview` puts the piece on a copy of the member (with one more of it in a copy of the bag, so a piece the party does not hold compares too) through core's `equip`, and builds both sides with `memberCombatant`, so the numbers cannot drift from a battle's. `wearers` are the lineup members whose categories allow the piece. Equipment adds no element affinities (core's "Not built yet"), so the resistances compared are status resistances.
* Bag order: the bag is kept by id (core's `Inventory` and `EquipmentBag` are maps), so it has no order to change or save; `bag(order)` lists it in a fixed order and nothing about the order reaches the save. The spec asks for no sort; Kind (field items, battle-only items, pieces by slot), Name and Count (most first) are this library's, ties going to the display name, then the id.
* Difficulty presets (BAT-120, UI-014): `difficulties()` lists core's presets in id order with core's name and the `desc.difficulty.<id>` description. BAT-126 lets them change any time outside battle; SAV-005 puts them in the save, so `setSettings` also refuses at the title, where there is none (`game.refuse.settings_no_game`), and `canChangeSettings()` says whether it would accept.
* Make macro (BAT-065, UI-011): `macroFromCombo` needs the combination in the combo log and builds one ability step per recipe component in the recipe's order, which fires an ordered recipe and any other, with default targets, which the macro rules re-pick each round anyway (BAT-053). Each component goes to a lineup member who knows the ability now, the one a component is tied to if it is; the members the log recorded are tried first, then the lineup in order, and a full assignment is searched for. With no assignment it is refused naming an ability no free member knows (`game.refuse.combo_no_member`). Name rules and slots are `createMacro`'s.
* Ambient party talk (FLD-073): the set party talk would play (FLD-072) comes up by itself as `OutputKind::Ambient` output the first time control returns to the field with player control after the party enters an area, warps included, while the profile's ambient talk is on. A set holds over one stretch of the story (its flag range), so "the first time in a story chapter" is kept as `<set>@<area>` in `World::ambientHeard`, which the save keeps; a set none of whose speakers is in the active party says nothing and is not marked heard. Ambient lines never take control and are not added to the text log, like party talk.
* Developer commands ([`docs/dev-tools.md`](../docs/dev-tools.md)): `devWarp`, `devWarpCell`, `devBattle`, `devVehicle` and `devRunEvent` work from the field only; `devGive`, `devMoney` and `devSetLevel` anywhere but the title and a battle (a battle holds its own copy of the party and the items); `devSetFlag` and `devEncounters` anywhere but the title; `devEndBattle` in a live battle. A command that runs marks the game (`World::devMarked`, saved in the `dev` chunk, never cleared, kept when an event restarts from its event-start world); a refused one changes nothing. A marked game writes no clear-data record (`game.clear_not_recorded` instead) and adds nothing to the pacing recorder from then on. A warp works like a script's (the vehicle ridden stays behind, load hooks, the area-entry autosave); a flag set by `devSetFlag` runs the area's flag hooks; `devGive` caps at `item_cap` and a negative count takes away; `devMoney` keeps the money between 0 and `money_cap`; `devSetLevel` sets the level with no experience into it and refills the member as a rest does, reviving it; `devBattle` starts a random-source battle (a vehicle battle aboard); `devEndBattle` sets every enemy's, or every party combatant's, hit points to 0 and resolves a round, so its record does not replay; `devEncounters(false)` stops visible enemies' contact and chases, random battles and battles aboard for the session only.
* Save text: `saveText` writes the save format with the interpreter's state while an event runs; during a battle it writes the world as the battle found it (the encounter stream from before the battle seed), so loading it sets an event battle up again and drops a field battle. `loadSaveText` loads it from the title like `load`, announced with `game.loaded_text`.
* Content hash: the hash a save's header and the clear-data record carry is built from the parsed data, not the files' bytes: `game.json` without its `presentation` block, the areas without `music`, the text tables without descriptions, and, as before, the dialogue tables, the journal, core's data hash and the script fingerprint.
